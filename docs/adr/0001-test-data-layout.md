# 0001. 評価データを座標系で分け、提供者名を含めない

日付: 2026-08-30
ステータス: 採用

## 背景

評価データが 2 つになった。自分で撮った追尾の一晩と、提供を受けた固定撮影の一晩である。

置き場は次のようになっていた。

```
/Volumes/Extreme SSD/pi_works/
├── meteor-composer-test/   追尾（自分の夜）
└── mave/                   固定（提供者の handle）
```

**片方が内容、片方が人名で、並びとして意味をなしていない。** どちらのデータかを知るには由来を知っている必要があり、初めて読む人には引けない。

同時に、公開してよい範囲の問題があった。提供者の handle と、機材（NIKON ZR / 24mm F4 / ISO1250）・撮影地・撮影時刻（23:25:20〜03:38:04）が同じ文書に並んでいる。**単体では公開情報でも、揃うと個人が特定できる。** この handle はコード内のコメントとテストにも入っており、`requirements.md` には「このデータで得た知見を公開する場合は提供者を明記すること」と書いてあった。**方針が逆を向いていた。**

## 決定

**1. ディレクトリは座標系で分ける。**

```
/Volumes/Extreme SSD/pi_works/meteor-composer-test/
├── test-sky/      追尾（空基準）
└── test-ground/   固定（地上基準）
```

スクリプトが分岐するのは座標系であって撮影者ではない。`requirements.md` 3.4 の空基準／地上基準にそのまま対応する。

**2. 提供を受けたデータの提供者名は、コードにもドキュメントにも書かない。** 書くのは観測条件（機材・露出・枚数・時間帯）だけにする。

**3. フォーラムでのやり取りを記録するときは、投稿へのリンクを残し、アカウント名は書かない。** 本文に要るのは誰が言ったかではなく何が分かったかで、辿る必要が出たらリンクから辿れる。

**唯一の例外は `docs/announcements/` である。** あれはフォーラム投稿の**本文そのもの**で、`[QUOTE="name"]` は BBCode の構文である。外すと引用として表示されない。**記録のために名前を書いているのではなく、投稿の側がそれを要求している。**

## 検討したが却下した案

- **`test-tracked` / `test-fixed`（架台で分ける）。** 架台と座標系は一対一ではない。**星が点像に写る短い固定撮影は空基準で処理できる**（1.2.0 より前はそれしか無かった）。架台で名付けると、この使い方を置く場所が無くなる。同じ取り違えを一度ドキュメントに書いて指摘されている
- **日付で分ける（`2026-08-12` / `2026-08-29`）。** 由来は一意になるが、**何が違うデータなのかが名前から消える**。増えたときに一覧が読めなくなる
- **提供者名を伏せ字にする（`contributor-a`）。** 名前が消えても「特定の誰か」という枠が残るだけで、ディレクトリ名が内容を語らない問題は直らない
- **handle だけ消して実測表はそのまま残す。** 機材・撮影時刻が揃っていれば、handle が無くても本人には結びつく。**指摘の半分しか直っていない**
- **「公開フォーラムに本人が書いたことなら handle を残してよい」という例外を作る。** **一度これで書いて、間違いだった。** データを預かった相手を伏せる理由（機材・時刻と揃うと個人が特定できる）を一般則に仕立て、そこに当てはまらない相手を例外側に置いただけで、**残してよい理由になっていない**。フォーラムで意見をもらった相手からは、そもそも何のデータも預かっていない。**リンクを残せば辿れるのだから、名前を書く必要が無い**

## 結果

- データの由来が名前から消えた。**これは意図的な損失である。** どちらが誰のデータかは、必要になったときに口頭で辿るしかない
- `tests/` 配下 35 ファイルの `DATA_ROOT` を書き換えた。**このパスはリポジトリの外にあるので、テストでは検出できない**。実行して初めて分かる
- `requirements.md` 3.4 の「提供者を明記すること」を反転させた。**明記する側の理由（提供してもらった事実への敬意）は消えていない**ので、公開しない場所——このリポジトリの外——で辿れるようにしておく必要がある
