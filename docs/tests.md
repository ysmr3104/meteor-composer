# テスト計画: MeteorComposer

> ステータス: ドラフト（実装前）
> 最終更新: 2026-08-16
> 準拠: t-wada 氏の自動テスト原則（テストサイズ分類・SMURF・古典派スタイル）

---

## 0. 前提と、このプロジェクト固有の制約

### PJSR は PixInsight プロセス内でしか動かない

`Image` / `StarDetector` / `IntegerResample` / `Dialog` は PJSR ネイティブオブジェクトで、Node.js には存在しません。これらに触れるコードは PixInsight を起動しないとテストできません。

### ただしヘッドレス自動実行はできる

manual-image-solver が実証済みで、GUI 操作なしにスクリプトを走らせられます。

```bash
/Applications/PixInsight/PixInsight.app/Contents/MacOS/PixInsight \
  -n --automation-mode --no-splash \
  -r="$(pwd)/tests/pjsr/<test>.js" \
  --force-exit
```

したがって **PJSR テストは「手動 Large」ではなく、自動化可能な Medium** として扱います。手動が必須なのは UI 操作の確認だけです。

### テストと評価を分ける

本プロジェクトで最も重要な区別です。

| | 目的 | 判定 | 頻度 |
|---|---|---|---|
| **テスト** | 昨日と同じ振る舞いをするか（回帰防止） | pass / fail が一意 | 毎回 |
| **検出性能評価** | 流星を見つけられるか、飛行機を弾けるか | 指標とベースライン比較 | データ更新時・アルゴリズム変更時 |

閾値 `k`、伸長比の倍率、スコアの重みは**単体テストでは一切検証できません**。これらは実データに対する評価でしか決められない。両者を混同すると、テストがデータの機嫌に左右される Flaky なものになります。

評価の枠組みは 5 章に分離して記述します。

## 1. テストサイズ分類（本プロジェクトでの定義）

| サイズ | 実行環境 | 対象 | 目安時間 | CI |
|---|---|---|---|---|
| **Small** | Node.js | 純粋 JavaScript のロジック全般 | 秒 | 可 |
| **Medium** | PixInsight ヘッドレス | PJSR API との接合、パイプライン結合 | 分 | 不可（ローカル） |
| **Large** | PixInsight GUI・手動 | UI 操作、実データでの通し確認 | 手動 | 不可 |

**Small を最大化し、Large を最小化する。** そのために設計を先に決めます（次章）。

## 2. テスト容易性が設計を決める（実装前に確定すべきこと）

### 境界を「プレーン配列」に置く

PJSR 依存を画像の読み込みと縮小までに閉じ込め、**それ以降を純粋 JavaScript にする**のが最重要の設計判断です。

```
┌─ PJSR 層（Medium でしかテストできない）────────────────┐
│ ImageWindow.open → getLuminance → resample(1/8)         │
│              → toMatrix() → toFloat32Array()            │
│              ↓                                          │
│   { data: Float32Array, width: int, height: int }       │  ← 境界
└─────────────────────────────────────────────────────────┘
┌─ 検出コア（純粋 JS / Small）────────────────────────────┐
│ 背景除去 → MAD 閾値 → 連結成分 → 2次モーメント          │
│              ↓                                          │
│   候補配列 [{ x0,y0,x1,y1, length, angle, elong, ... }] │
└─────────────────────────────────────────────────────────┘
┌─ 候補処理（純粋 JS / Small・画像に一切触れない）────────┐
│ 共線マージ → フレーム横断照合 → 分類スコアリング        │
└─────────────────────────────────────────────────────────┘
┌─ UI 層（Large・手動）───────────────────────────────────┐
│ PJSR Dialog、プレビュー、候補リスト、直線のドラッグ操作 │
└─────────────────────────────────────────────────────────┘
```

この境界の効果:

- **検出コア全体が Node.js でテストできる。** 合成画像（配列に線を描いたもの）をフィクスチャにできる
- **3rd pass（衛星・飛行機判定）は完全に Small。** 候補リストしか扱わないため、画像も PixInsight も不要
- PJSR 層が薄くなり、Medium テストの対象が「読み込めるか・縮小できるか」に絞られる

**境界の変換コストは実測で無視できる**（requirements.md「PJSR API 実地調査の結果」参照）。

| 処理 | 実測 |
|---|---|
| `toMatrix()` + `toArray()` | 約 3.3 ms |
| `ImageWindow.open()` 1 枚 | 466 ms |

読み込みが 466 ms を占めるので、境界変換の 3.3 ms は誤差の範囲。**テスト容易性のために性能を犠牲にしていない。**

なお `Matrix` は `MAD` / `median` / `Sn` / `Qn` などのロバスト統計をネイティブに持つ。将来 PJSR 側で計算した方が速い場面が出ても、**検出コアは純粋 JS 実装を保持する**こと。そこが Small テストの対象であり、ネイティブ版は最適化として並置するに留める。両者が食い違ったときに気づけるよう、同一入力で結果を突き合わせる Medium テストを置く。

TEST.md §9 の「引数経由で依存を渡す（最推奨）」をモジュール境界のレベルで適用したものです。

### モジュール構成と両対応

既存 2 本と同じ方式を踏襲します。純粋 JS モジュールの末尾にガードを置き、PJSR では `#include`、Node.js では `require` で読みます。

```javascript
if (typeof module !== "undefined") {
   module.exports = { detectCandidates: detectCandidates, ... };
}
```

想定するファイル分割:

| ファイル | 性質 | テストサイズ |
|---|---|---|
| `javascript/detection_core.js` | 純粋 JS。背景除去・閾値・連結成分・モーメント | Small |
| `javascript/candidate_ops.js` | 純粋 JS。共線マージ・横断照合・スコアリング | Small |
| `javascript/mask_geometry.js` | 純粋 JS。半平面判定・キーフレーム補間・面積計算・辺バンドの変換・マスク画像の閾値・オーバーレイのラン抽出 | Small |
| `javascript/pjsr_image_io.js` | PJSR 専用。XISF 読み込み・輝度抽出・縮小 | Medium |
| `javascript/MeteorComposer.js` | PJSR 専用。UI とパイプライン統合 | Medium / Large |

本体には `__METEOR_COMPOSER_LIBRARY_MODE` 相当のフラグを設け、`#include` しても実行されないようにします（split-image-solver と同じ手法）。

## 3. Small テスト（Node.js）

### 3-1. 対象

| 対象 | 検証内容 |
|---|---|
| 2次モーメント → 伸長比・方位角・始終点 | 解析的に既知の形状に対する厳密値 |
| 連結成分ラベリング | 分離した塊の個数、対角接続の扱い、境界の扱い |
| 背景除去（縮小→拡大→差分） | 一様な勾配を与えて平坦化されること。細い線が消えないこと |
| MAD ベースの閾値決定 | 既知の分布に対する閾値。外れ値（流星）に汚染されないこと |
| 共線マージ | 一直線上の断片が 1 本になること。平行だが別線が統合されないこと |
| フレーム横断照合 | 連続フレームで滑らかに移動する候補を同一物体と判定 |
| 分類スコアリング | 特徴量ベクトル → スコアの単調性、カットオフの境界 |
| 半平面マスク | 内外判定、回転、キーフレーム補間、除外面積 |
| 候補リストの JSON 入出力 | 往復（serialize → deserialize で不変） |

### 3-2. 自作自演を避ける具体策

**モーメント計算の期待値は、実装とは独立に導出する。**

ここで**離散化の扱いが期待値を変える**ので、先に整理します。

連続的な w×h の一様矩形の 2 次モーメント（分散）は `w²/12`, `h²/12` です。しかし**ピクセルは離散**なので、実際に計算されるのは等間隔な N 個の整数の分散 `(N²-1)/12` になります。40×2 の矩形なら伸長比は 20 ではなく `√((40²-1)/(2²-1))` ≒ 23.09 です。

そこで実装は**シェパード補正**（ビン化されたデータの標準的な補正）を採用し、対角モーメントに `1/12` を加えて連続値を回復します。

```
補正あり: m20 = w²/12,  m02 = h²/12   → 伸長比 = w/h（厳密）
補正なし: m20 = (w²-1)/12             → 伸長比 = √((w²-1)/(h²-1))
```

補正には副次的だが重要な効果があります。**幅 1px の線は補正なしだと `m02 = 0` でゼロ除算になります。** 補正すると `m02 = 1/12` となり、50×1 の線の伸長比は 50 と有限かつ直感的な値になります。流星は細い線なので、この退化ケースは日常的に発生します。

シェパード補正は軸平行なビン化にのみ妥当なので、`computeMoments(points, applySheppard)` の第2引数で切り替えられるようにしてあります。

| フィクスチャ | 期待値（独立に導出） | 補正 |
|---|---|---|
| 40×2 px の矩形 | 伸長比 20.0、方位角 0° | あり |
| 50×1 px の線 | 伸長比 50.0（ゼロ除算しないこと） | あり |
| 10×10 px の正方形 | 伸長比 1.0 | あり |
| 単一ピクセル | 伸長比 1.0（退化ケース） | あり |
| 40×2 px の矩形 | 伸長比 √((40²-1)/(2²-1)) | なし |
| 40×3 を 15/30/45/60/90/120/170° 回転 | 方位角＝回転角、伸長比は不変 | なし |

**回転テストは実座標で行います。** ラスタライズすると量子化誤差が入り、本物のバグを覆い隠します。正確な座標を回転させれば情報は失われないので、**伸長比は厳密に不変、方位角は厳密に回転角と一致**しなければなりません（許容誤差 1e-9）。回転後は軸平行でなくなるため、補正は両辺で無効にします。

**禁止**: 実装の `computeMoments()` を呼んで期待値を作ること。

**往復テストの限界に注意**: 既存 2 本は round-trip（`deproject(project(x)) == x`）を多用しています。有効ですが、順逆で相殺する誤差は検出できません。**絶対値の検証と組み合わせる**こと。

### 3-3. 合成フィクスチャの生成

配列に線・点・勾配を描くヘルパーを `tests/fixtures/synthetic.js` に置きます。

- `makeGradientField(w, h, slope)` — 背景除去の検証用
- `makeLine(w, h, x0, y0, x1, y1, width, amplitude)` — 流星・衛星の模擬
- `makeStarField(w, h, count, fwhm, seed)` — 星の模擬。**seed 固定で決定的に**
- `addGaussianNoise(field, sigma, seed)` — 閾値検証用。**seed 固定**

乱数は必ず seed を取る自前実装にします。`Math.random()` を使うと Flaky になります。

## 4. Medium テスト（PixInsight ヘッドレス）

### 4-1. 対象

Small で担保できない「PJSR API が期待通りに動くか」だけに絞ります。

| 対象 | 検証内容 |
|---|---|
| XISF 読み込み | registered ファイルを開いて寸法・チャンネル数が取れる |
| 輝度抽出 | カラー画像から 1ch が得られる |
| 縮小 | 1/8 に縮小した配列の寸法と、線が保存されていること |
| `StarDetector` | 合成星野に対して既知個数の星が検出される |
| 無効領域（ゼロ埋め）の検出 | registered 周辺のゼロ領域が除外される |
| パイプライン結合 | 読み込み → 検出コア → 候補配列 まで通ること |

### 4-2. Fragile Test を避ける

**PJSR オブジェクトをモックして呼び出しを検証してはいけません。**

```javascript
// 悪い例: 実装への密結合。resample の呼び方を変えるとテストが壊れる
assertCalledWith(mockImage.resample, 0.125);

// 良い例: 出力を検証する。実装手段が変わっても壊れない
var out = downsample(img, 8);
assertEqual(out.width, 750);
assertEqual(out.height, 500);
```

Medium テストでは**本物の `Image` を使う**（古典派）。TestDouble を使うのはテストサイズを下げる目的のときだけです。

### 4-3. 実行基盤

split-image-solver の `tests/pjsr/pjsr_test_framework.js`（アサーション + JSON 結果出力 + `console.writeln` のキャプチャ）を流用します。新規に作りません。

### 4-4. Flaky リスク

PixInsight の起動には数十秒かかり、ライセンス状態や GUI の初期化に依存します。**Medium テストは意図的に少数に保ちます。** Small で書けるものを Medium に置かないこと。

## 5. 検出性能評価（テストではない）

### 5-1. なぜ分けるか

閾値やスコアの重みは実データでしか決まりません。これをテストスイートに入れると、データを差し替えるたびに「失敗」が出て、テスト結果が信用されなくなります（Google の 1% Flaky 問題）。

### 5-2. 評価データセット

**2 つある。座標系が違うので、両方でないと測れないことがある。**

```
/Volumes/Extreme SSD/pi_works/meteor-composer-test/
├── test-sky/      追尾（空基準）  2026-08-12 ペルセウス座・自分の夜
└── test-ground/   固定（地上基準）提供データ
```

ディレクトリ名は**座標系**で付けている。撮影者でも日付でもない。スクリプトが分岐するのがそこだからで、`requirements.md` 3.4 の空基準／地上基準にそのまま対応する。**提供者の名前は入れない**（`docs/adr/0001-test-data-layout.md`）。

#### 5-2-1. test-sky（追尾）

以下は WBPP 実行中に確認した実測情報。

##### 撮影条件

| 項目 | 値 |
|---|---|
| 撮影日 | 2026-08-12（ペルセウス座流星群） |
| カメラ | Sony ILCE-7M3（α7III、フルサイズ 6024×4024） |
| レンズ | 20mm |
| 露出 | 13 秒 |
| 架台 | **赤道儀による追尾** |
| 時間帯 | 00:52 〜 02:53（約 2 時間） |
| 正解の流星 | **9 個**（01:18 〜 02:53 の範囲） |

派生する数値:

- 水平画角 約 84°、対角画角 約 94°
- ピクセルスケール 約 50 秒角/px（0.84 分角/px）
- **1° の流星 ≒ 72px、5° ≒ 359px** — 星（FWHM 数 px）との伸長比の差は十分大きい

##### このデータセットが検証できること

**追尾撮影のため、地上物は registered 座標系で移動する。** しかも撮影開始付近のフレームにのみ地上が写り込み、時間とともにフレーム外へ流れていく。

- 地上物は星に対して 15°/時 で移動する。2 時間で約 30°、**画角 84° に対しておよそフレーム幅の 36% を横切る**
- したがって **Tier 1（静的な半平面）では一晩をカバーできない**。序盤のフレームに合わせると後半は過剰にマスクし、後半に合わせると序盤の地上が露出する
- **Tier 2（キーフレーム補間）の必要性を実証できる、ちょうど良いデータ**

一方、固定撮影のケース（requirements.md 3.2 の推奨撮影時間の表）はこのデータセットでは検証できない。それが `test-ground` である。

##### ディレクトリ構成とファイル名

```
/Volumes/Extreme SSD/pi_works/meteor-composer-test/test-sky/
├── answer/                              目視で確認した正解（JPG・9件）
│   └── pct-2026-08-12_011807_ILCE-7M3_DSC05001.JPG
└── registered/
    └── Light_BIN-1_6024x4024_EXPOSURE-13.00s_FILTER-NoFilter_RGB/
        ├── pct-2026-08-12_005232_ILCE-7M3_DSC04904_d_r.xisf
        └── pct-2026-08-12_005232_ILCE-7M3_DSC04904_d_r.xdrz
```

**対応規則**: `answer` の拡張子を除いた stem が、registered 側ファイル名の前方一致になる。registered 側には `_d_r`（debayer + register）が付く。

```
answer:      pct-2026-08-12_011807_ILCE-7M3_DSC05001.JPG
registered:  pct-2026-08-12_011807_ILCE-7M3_DSC05001_d_r.xisf
```

**実装時の注意**（requirements.md の入力仕様にも反映が必要）:

- **`registered/` 直下ではなく、撮影パラメータごとのグループサブディレクトリの下にある。** 再帰探索するか、グループを選択する UI が要る
- **`.xdrz`（drizzle データ）が同じディレクトリに同居する。** 拡張子でのフィルタが必須

##### ground_truth.json

`answer/` の JPG から機械的に生成できる（ファイル名の突き合わせのみ）。座標は目視での追記。

```json
{
  "session": "2026-08-12-perseids",
  "registered_dir": "Light_BIN-1_6024x4024_EXPOSURE-13.00s_FILTER-NoFilter_RGB",
  "meteors": [
    { "file": "pct-2026-08-12_011807_ILCE-7M3_DSC05001_d_r.xisf",
      "x0": null, "y0": null, "x1": null, "y1": null }
  ],
  "known_false_positives": [],
  "uncertain": []
}
```

##### 座標が無いと何が測れないか（要対応）

現在 `x0`〜`y1` は `null` である。この状態で測れるのは**フレーム単位の recall だけ**、つまり「正解のファイルから候補が 1 件以上出たか」に限られる。

**これは「流星を検出できたか」とは違う。** 1 フレームに複数の候補が出るため。

実例として 2026-08-12 の `DSC05443`（753×503 の作業解像度）は 3 件の候補を返した。

| | 中心 | 始点 → 終点 | 長さ | 方位角 |
|---|---|---|---|---|
| [0] | (186, 50) | (194,35) → (179,63) | 31.8 | 118.0° |
| [1] | (439, 90) | (454,86) → (423,96) | 32.5 | 159.4° |
| [2] | (597,187) | (607,175) → (587,199) | 31.2 | 128.2° |

**どれが流星かを機械的に特定できない。** 極端な場合、衛星を 3 本検出して流星を見落としていても、現在の評価は「検出成功」と数える。

このケースでは軌跡長（[0] は 14 フレーム、[2] は 11 フレーム、[1] は 2 フレーム）から [1] が流星だと推測できたが、これは横断照合の結果を人が読んで判断したのであって、評価が自動でできたわけではない。

##### 座標はスクリーニング UI で作る（決定事項）

**座標を人手で入力させてはならない。** 人にしか出せない情報は「複数の候補のうちどれが流星か」という判断だけであり、座標はその候補が既に持っている。判断さえもらえれば座標は候補から取れる。

そこで **Stage 2 のスクリーニング UI に正解データの出力機能を持たせる**。UI は候補を表示して採否を判断させるものなので、「この候補が流星である」と記録する機能はその自然な拡張になる。専用ツールを別途作る必要はない。

出力される正解データは、選ばれた候補の座標をそのまま持つ。

```json
{ "file": "pct-..._DSC05443_d_r.xisf",
  "x0": 454, "y0": 86, "x1": 423, "y1": 96,
  "labeled_by": "human", "screen_factor": 8 }
```

##### 正解作成モードの必須要件（自作自演を避けるため）

**UI が分類器の判定を見せた状態で人に選ばせると、正解データが分類器に引きずられる。** それを使って同じ分類器を評価すれば、データセット規模の自作自演になる（TEST.md の「自作自演テスト」がデータ側に現れた形）。

したがって正解作成モードでは、

- **検出を意図的に緩い設定で走らせる**（下記）
- **全候補を表示する。** 衛星フィルタやスコアで絞り込まない
- **分類器の判定・スコアを表示しない**、または明示的に隠せるようにする
- 表示順を分類器のスコア順にしない（提示順自体が誘導になる）

通常のスクリーニングモードでは逆に絞り込みとスコア順が有用なので、**2 つのモードは明確に分ける**。

##### 正解作成は緩い設定で検出する（重要）

**運用設定で検出した候補だけから選ばせると、正解データが検出器の性能に上限を縛られる。**

運用設定（`k=5.0`、`minElongation=6.0`、`minPixels=12`）が淡い流星を落としていた場合、その流星はそもそも候補に現れないので人は選べない。結果、正解には「検出器が見つけられたもの」しか入らず、それに対する recall は常に高く出る。**「検出できたものは検出できた」という同語反復**にしかならず、見逃しを測るという目的を果たさない。

そこで正解作成モードでは**閾値を大きく緩めて走らせ**、運用設定なら捨てていた候補まで提示する。

**これらの閾値はすべて UI から変更できるようにする。既定値は別途検討する（未決事項）。** 以下は現時点の暫定値であり、根拠のある数字ではない。

| パラメータ | 現在の運用値 | 正解作成モードの暫定値 |
|---|---|---|
| `k`（閾値のσ数） | 5.0 | 2.5〜3.0 |
| `minElongation` | 6.0 | 3.0 |
| `minPixels` | 12 | 6 |
| `minLength` | 10.0 | 5.0 |

候補数は大幅に増えるが、**正解作成は一度きりの作業**であり、通常のスクリーニングとは頻度が違う。人が見る量が増えるコストと、正解が検出器から独立するという利得を比べれば後者が勝る。

どこまで緩めるかは、**実際に走らせて候補数と見つかる流星の数を見ながら決める**性質のもので、机上では決まらない。UI で触れるようにしておけば、その調整自体をユーザーが行える。

この方式には副次的な利得もある。目視で見落とされやすいのは「淡い・短い・画面端」の流星であり、緩い設定はまさにそこを拾う。**目視ラベルの見落とし（5-3-1）を埋める手段にもなる。**

緩い設定で拾った候補を人が流星と確認したら、`answer/` とベースラインを更新する。

##### 突き合わせの方法

候補との対応付けは、**中心座標が許容半径以内**かつ**方位角が許容差以内**で判定する（許容値は実装時に決める）。始点と終点の入れ替わりは評価側で吸収する。

これが入ると次が測れるようになる。

- 検出した候補が**本当に流星か**（候補単位の recall）
- 衛星フィルタが**流星を巻き添えにしていないか**
- 位置と方位角の精度

#### 5-2-2. test-ground（固定）

提供を受けた固定撮影の一晩。**空基準の経路では扱えないことが分かった、その現物である**（`requirements.md` 3.4）。

##### 撮影条件

| 項目 | 値 |
|---|---|
| カメラ | NIKON ZR（6064×4040） |
| レンズ | 24mm F4 / ISO1250 |
| 露出 | 13 秒 × **1045 枚** |
| 架台 | **固定三脚** |
| 時間帯 | 23:25:20 〜 03:38:04（**4 時間 13 分**、日付をまたぐ） |
| 空の回転量 | 約 63° |
| 正解の流星 | **未確定**（スクリーニング未実施。検出は 321 件） |

##### このデータセットが検証できること

- **地上基準の経路そのもの。** `registered/` は 1045 枚のうち 718 枚しか solve できず、残った枚も平均 36.5% が無データ領域になる。`debayered/` は 1045 枚すべてが全センサー面で、無データ領域が無い。この対比は空基準のデータでは作れない
- **深い除外マスク。** 下端 21% のマスクで、`downsample()` がマスク領域を 0 のまま残す不具合を出した（`requirements.md` 5.10）。空基準側のマスクは浅く、**このデータで初めて出た**
- **日付をまたぐ DATE-OBS。** 23 時台に始まり 3 時台に終わるので、フレーム間隔を素直に引き算すると負になる（`test_coordinate_system.js`）
- **中央値スタック背景**（`probe_median_background.js`）。1 枚・5 枚・15 枚・31 枚のノイズと星の流れの引き換え

##### このデータセットで測れないこと

**recall が測れない。** 正解ラベルが無いためで、スクリーニングを終えるまで「流星を落としていないか」は言えない。現状の根拠は判定 3 本ぶんしか無い。

### 5-3. 指標とゲート

| 指標 | 定義 | ゲート |
|---|---|---|
| **Recall（再現率）** | 正解の流星のうち検出できた割合 | **ハードゲート。ベースラインから 1 本でも減ったら NG** |
| 要確認の検出数 | 正解に無い検出の件数 | 報告のみ。**偽陽性として扱わない**（5-3-1 参照） |
| 衛星・飛行機の棄却率 | `known_false_positives` を弾けた割合 | 報告のみ |
| 処理時間 / フレーム | 1st pass の 1 枚あたり | 報告のみ。目安 500 枚が実用時間内 |

**Recall だけをハードゲートにするのは意図的です。** 要件で「デフォルトは取りこぼさない側に振る／後段に人間のスクリーニングがある」と決めているため、誤検出が増えることの損失は小さく、見逃しの損失が大きい。

split-image-solver の「ベースラインからの劣化は即 NG。テスト側に許容幅があっても許容範囲内と判断してはならない」というルールをそのまま適用します。性能が向上した場合はベースラインを更新します。

### 5-3-1. 正解ラベルは recall の下限である（重要）

**`answer/` に無い検出を、機械的に偽陽性としてカウントしてはならない。**

正解は人間の目視によるもので、本人の申告どおり「誤検出は無いが見落としはあるかもしれない」性質を持つ。つまり:

| | 意味 |
|---|---|
| `answer` にある 9 件 | **確実に流星**。検出できなければ見逃し |
| `answer` に無い検出 | **偽陽性とは断定できない**。人が見落とした本物の流星が混じりうる |

したがって指標はこう扱う。

- **Recall = 9 件中いくつ検出できたか。** これがハードゲート
- **`answer` 外の検出は「要確認」として件数を報告するだけ。** 偽陽性率として扱わない
- 要確認の中身を目視し、本物と判明したら **`answer` に追加してベースラインを更新する**

この扱いを守らないと、アルゴリズムが正しく見つけた淡い流星が偽陽性として計上され、**改善が退化に見える**。実際、人間が見落としやすいのは「淡い・短い・画面端」の流星であり、そこはまさにアルゴリズムの改善で拾えるようになる領域。評価設計が改善を罰する構造になってはいけない。

淡いものを拾えるようになるほど要確認件数は増えるので、この数値の増加自体は悪い兆候ではない。

### 5-4. データセットの作り方

**2026-08-12 セッションは目視ラベリング済み**（`answer/` に 9 件）。作業は以下の状態。

- [x] WBPP で registered まで通す（実行中 → 完了待ち）
- [x] 全フレームを目視し、流星が写ったフレームを特定する
- [ ] `answer/` のファイル名から `ground_truth.json` を生成する（機械的に可能）
- [ ] 衛星・飛行機と分かるものを `known_false_positives` に記録する（未着手）
- [ ] 初回ベースラインの確定

始終点座標は当初 `null` でよい（5-2 参照）。フレーム単位の recall はファイル名の突き合わせだけで測れる。

新しいセッションを追加する場合も同じ手順。**判断に迷ったフレームは `uncertain` として分離し、指標の分母から外す。** 曖昧なものを正解に含めるとベースラインが不安定になる。

## 9. SMURF による自己評価

| 軸 | 評価 | 備考 |
|---|---|---|
| **Speed** | 良 | Small が大半で秒オーダー。Medium は少数に限定 |
| **Maintainability** | 良 | 境界をプレーン配列に置き、PJSR への依存を局所化 |
| **Utilization** | **課題** | Medium は PixInsight が必要で CI に載らない。Small のみ CI 化を検討 |
| **Reliability** | 良 | 乱数は seed 固定。Medium を少数に保つ |
| **Fidelity** | **課題** | 合成フィクスチャは実データの複雑さ（薄雲、密集星野、レンズ収差）を再現しない。ここは 5 章の評価が補う |

Fidelity と Reliability のトレードオフを、**テスト（合成・決定的・高信頼）と評価（実データ・高忠実）を分離すること**で解いている構造です。
