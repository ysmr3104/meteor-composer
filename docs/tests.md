# テスト計画: MeteorComposer

> ステータス: ドラフト（実装前）
> 最終更新: 2026-08-16
> 準拠: t-wada 氏の自動テスト原則（テストサイズ分類・SMURF・古典派スタイル）

---

## 0. 前提と、このプロジェクト固有の制約

### PJSR は PixInsight プロセス内でしか動かない

`Image` / `StarDetector` / `IntegerResample` / `Dialog` は PJSR ネイティブオブジェクトで、Node.js には存在しません。これらに触れるコードは PixInsight を起動しないとテストできません。

### ただしヘッドレス自動実行はできる

manual-image-solver が実証済みで、GUI 操作なしにスクリプトを走らせられます。

```bash
/Applications/PixInsight/PixInsight.app/Contents/MacOS/PixInsight \
  -n --automation-mode --no-splash \
  -r="$(pwd)/tests/pjsr/<test>.js" \
  --force-exit
```

したがって **PJSR テストは「手動 Large」ではなく、自動化可能な Medium** として扱います。手動が必須なのは UI 操作の確認だけです。

### テストと評価を分ける

本プロジェクトで最も重要な区別です。

| | 目的 | 判定 | 頻度 |
|---|---|---|---|
| **テスト** | 昨日と同じ振る舞いをするか（回帰防止） | pass / fail が一意 | 毎回 |
| **検出性能評価** | 流星を見つけられるか、飛行機を弾けるか | 指標とベースライン比較 | データ更新時・アルゴリズム変更時 |

閾値 `k`、伸長比の倍率、スコアの重みは**単体テストでは一切検証できません**。これらは実データに対する評価でしか決められない。両者を混同すると、テストがデータの機嫌に左右される Flaky なものになります。

評価の枠組みは 5 章に分離して記述します。

## 1. テストサイズ分類（本プロジェクトでの定義）

| サイズ | 実行環境 | 対象 | 目安時間 | CI |
|---|---|---|---|---|
| **Small** | Node.js | 純粋 JavaScript のロジック全般 | 秒 | 可 |
| **Medium** | PixInsight ヘッドレス | PJSR API との接合、パイプライン結合 | 分 | 不可（ローカル） |
| **Large** | PixInsight GUI・手動 | UI 操作、実データでの通し確認 | 手動 | 不可 |

**Small を最大化し、Large を最小化する。** そのために設計を先に決めます（次章）。

## 2. テスト容易性が設計を決める（実装前に確定すべきこと）

### 境界を「プレーン配列」に置く

PJSR 依存を画像の読み込みと縮小までに閉じ込め、**それ以降を純粋 JavaScript にする**のが最重要の設計判断です。

```
┌─ PJSR 層（Medium でしかテストできない）────────────────┐
│ XISF 読み込み → 輝度抽出 → 1/8 縮小                     │
│              ↓                                          │
│   { data: Float32Array, width: int, height: int }       │  ← 境界
└─────────────────────────────────────────────────────────┘
┌─ 検出コア（純粋 JS / Small）────────────────────────────┐
│ 背景除去 → MAD 閾値 → 連結成分 → 2次モーメント          │
│              ↓                                          │
│   候補配列 [{ x0,y0,x1,y1, length, angle, elong, ... }] │
└─────────────────────────────────────────────────────────┘
┌─ 候補処理（純粋 JS / Small・画像に一切触れない）────────┐
│ 共線マージ → フレーム横断照合 → 分類スコアリング        │
└─────────────────────────────────────────────────────────┘
┌─ UI 層（Large・手動）───────────────────────────────────┐
│ PJSR Dialog、プレビュー、候補リスト、直線のドラッグ操作 │
└─────────────────────────────────────────────────────────┘
```

この境界の効果:

- **検出コア全体が Node.js でテストできる。** 合成画像（配列に線を描いたもの）をフィクスチャにできる
- **3rd pass（衛星・飛行機判定）は完全に Small。** 候補リストしか扱わないため、画像も PixInsight も不要
- PJSR 層が薄くなり、Medium テストの対象が「読み込めるか・縮小できるか」に絞られる

TEST.md §9 の「引数経由で依存を渡す（最推奨）」をモジュール境界のレベルで適用したものです。

### モジュール構成と両対応

既存 2 本と同じ方式を踏襲します。純粋 JS モジュールの末尾にガードを置き、PJSR では `#include`、Node.js では `require` で読みます。

```javascript
if (typeof module !== "undefined") {
   module.exports = { detectCandidates: detectCandidates, ... };
}
```

想定するファイル分割:

| ファイル | 性質 | テストサイズ |
|---|---|---|
| `javascript/detection_core.js` | 純粋 JS。背景除去・閾値・連結成分・モーメント | Small |
| `javascript/candidate_ops.js` | 純粋 JS。共線マージ・横断照合・スコアリング | Small |
| `javascript/mask_geometry.js` | 純粋 JS。半平面判定・キーフレーム補間・面積計算 | Small |
| `javascript/pjsr_image_io.js` | PJSR 専用。XISF 読み込み・輝度抽出・縮小 | Medium |
| `javascript/MeteorComposer.js` | PJSR 専用。UI とパイプライン統合 | Medium / Large |

本体には `__METEOR_COMPOSER_LIBRARY_MODE` 相当のフラグを設け、`#include` しても実行されないようにします（split-image-solver と同じ手法）。

## 3. Small テスト（Node.js）

### 3-1. 対象

| 対象 | 検証内容 |
|---|---|
| 2次モーメント → 伸長比・方位角・始終点 | 解析的に既知の形状に対する厳密値 |
| 連結成分ラベリング | 分離した塊の個数、対角接続の扱い、境界の扱い |
| 背景除去（縮小→拡大→差分） | 一様な勾配を与えて平坦化されること。細い線が消えないこと |
| MAD ベースの閾値決定 | 既知の分布に対する閾値。外れ値（流星）に汚染されないこと |
| 共線マージ | 一直線上の断片が 1 本になること。平行だが別線が統合されないこと |
| フレーム横断照合 | 連続フレームで滑らかに移動する候補を同一物体と判定 |
| 分類スコアリング | 特徴量ベクトル → スコアの単調性、カットオフの境界 |
| 半平面マスク | 内外判定、回転、キーフレーム補間、除外面積 |
| 候補リストの JSON 入出力 | 往復（serialize → deserialize で不変） |

### 3-2. 自作自演を避ける具体策

**モーメント計算の期待値は、実装とは独立に導出する。**

w×h の一様な矩形の 2 次モーメント（分散）は `w²/12`, `h²/12` です。したがって伸長比は `h/w` に厳密に一致します。この導出は実装を見ずに得られるので、自作自演になりません。

| フィクスチャ | 期待値（独立に導出） |
|---|---|
| 40×2 px の矩形 | 伸長比 20.0、方位角 0° |
| 上を 30° 回転 | 方位角 30°、伸長比は不変 |
| 10×10 px の正方形 | 伸長比 1.0 |
| 単一ピクセル | 伸長比 1.0（退化ケース） |

**禁止**: 実装の `computeMoments()` を呼んで期待値を作ること。

**往復テストの限界に注意**: 既存 2 本は round-trip（`deproject(project(x)) == x`）を多用しています。有効ですが、順逆で相殺する誤差は検出できません。**絶対値の検証と組み合わせる**こと。

### 3-3. 合成フィクスチャの生成

配列に線・点・勾配を描くヘルパーを `tests/fixtures/synthetic.js` に置きます。

- `makeGradientField(w, h, slope)` — 背景除去の検証用
- `makeLine(w, h, x0, y0, x1, y1, width, amplitude)` — 流星・衛星の模擬
- `makeStarField(w, h, count, fwhm, seed)` — 星の模擬。**seed 固定で決定的に**
- `addGaussianNoise(field, sigma, seed)` — 閾値検証用。**seed 固定**

乱数は必ず seed を取る自前実装にします。`Math.random()` を使うと Flaky になります。

## 4. Medium テスト（PixInsight ヘッドレス）

### 4-1. 対象

Small で担保できない「PJSR API が期待通りに動くか」だけに絞ります。

| 対象 | 検証内容 |
|---|---|
| XISF 読み込み | registered ファイルを開いて寸法・チャンネル数が取れる |
| 輝度抽出 | カラー画像から 1ch が得られる |
| 縮小 | 1/8 に縮小した配列の寸法と、線が保存されていること |
| `StarDetector` | 合成星野に対して既知個数の星が検出される |
| 無効領域（ゼロ埋め）の検出 | registered 周辺のゼロ領域が除外される |
| パイプライン結合 | 読み込み → 検出コア → 候補配列 まで通ること |

### 4-2. Fragile Test を避ける

**PJSR オブジェクトをモックして呼び出しを検証してはいけません。**

```javascript
// 悪い例: 実装への密結合。resample の呼び方を変えるとテストが壊れる
assertCalledWith(mockImage.resample, 0.125);

// 良い例: 出力を検証する。実装手段が変わっても壊れない
var out = downsample(img, 8);
assertEqual(out.width, 750);
assertEqual(out.height, 500);
```

Medium テストでは**本物の `Image` を使う**（古典派）。TestDouble を使うのはテストサイズを下げる目的のときだけです。

### 4-3. 実行基盤

split-image-solver の `tests/pjsr/pjsr_test_framework.js`（アサーション + JSON 結果出力 + `console.writeln` のキャプチャ）を流用します。新規に作りません。

### 4-4. Flaky リスク

PixInsight の起動には数十秒かかり、ライセンス状態や GUI の初期化に依存します。**Medium テストは意図的に少数に保ちます。** Small で書けるものを Medium に置かないこと。

## 5. 検出性能評価（テストではない）

### 5-1. なぜ分けるか

閾値やスコアの重みは実データでしか決まりません。これをテストスイートに入れると、データを差し替えるたびに「失敗」が出て、テスト結果が信用されなくなります（Google の 1% Flaky 問題）。

### 5-2. 評価データセット

```
tests/eval/dataset/
├── <session-name>/
│   ├── registered/          WBPP 出力（git 管理外・パスを設定で指定）
│   └── ground_truth.json    目視でラベル付けした正解
```

`ground_truth.json` の想定:

```json
{
  "session": "2026-08-12-perseids",
  "frames": 573,
  "meteors": [
    { "file": "light_0123_r.xisf", "x0": 1820, "y0": 640, "x1": 2450, "y1": 1180 }
  ],
  "known_false_positives": [
    { "file": "light_0088_r.xisf", "type": "satellite" },
    { "file": "light_0140_r.xisf", "type": "aircraft" }
  ]
}
```

### 5-3. 指標とゲート

| 指標 | 定義 | ゲート |
|---|---|---|
| **Recall（再現率）** | 正解の流星のうち検出できた割合 | **ハードゲート。ベースラインから 1 本でも減ったら NG** |
| False positive / frame | 1 フレームあたりの誤検出数 | 報告のみ。緩い上限のみ設定 |
| 衛星・飛行機の棄却率 | 既知の誤検出源を弾けた割合 | 報告のみ |
| 処理時間 / フレーム | 1st pass の 1 枚あたり | 報告のみ。目安 500 枚が実用時間内 |

**Recall だけをハードゲートにするのは意図的です。** 要件で「デフォルトは取りこぼさない側に振る／後段に人間のスクリーニングがある」と決めているため、誤検出が増えることの損失は小さく、見逃しの損失が大きい。

split-image-solver の「ベースラインからの劣化は即 NG。テスト側に許容幅があっても許容範囲内と判断してはならない」というルールをそのまま適用します。性能が向上した場合はベースラインを更新します。

### 5-4. データセットの作り方（今夜の WBPP 後）

1. WBPP で registered まで通す
2. Blink 等で全フレームを目視し、流星が写ったフレームを特定する
3. 各流星のおおよその始終点座標を記録する
4. 衛星・飛行機と分かるものも `known_false_positives` に記録する

**この目視ラベリングが評価の土台**であり、ここの精度が全体の上限を決めます。判断に迷ったフレームは `uncertain` として分離し、指標の分母から外すのが安全です。

## 6. Large テスト（手動）

自動化しないものだけを列挙します。増やさないこと。

- プレビュー上での直線のドラッグ操作と、除外領域のシェーディング表示
- 候補リストのヘッダクリックソート、採否トグル
- ズーム・パン、オートストレッチの切り替え
- 実データ 1 セッションの通し実行（検出 → スクリーニング → 出力）
- 中断機能が効くこと

手順は本ドキュメントの改訂時に追記します。

## 7. Phase 1 で書くテスト

実装と並行して用意するもの。

**Small（優先度: 最高）**

- [ ] モーメント計算 — 解析的既知値 4 ケース以上
- [ ] 連結成分ラベリング — 分離・接続・境界
- [ ] 背景除去 — 勾配の平坦化、線の保存
- [ ] MAD 閾値 — 外れ値耐性
- [ ] 共線マージ — 統合されるべき／されるべきでないケース
- [ ] 半平面マスク — 内外判定・回転・面積
- [ ] 候補リストの JSON 往復
- [ ] 合成フィクスチャ生成ヘルパー（seed 固定）

**Medium**

- [ ] XISF 読み込み → 輝度抽出 → 縮小の寸法検証
- [ ] `StarDetector` の戻り値構造の確認（**実装前の API 調査を兼ねる**）
- [ ] 読み込み → 検出コア の結合

**評価**

- [ ] `ground_truth.json` のラベリング
- [ ] 評価スクリプトと初回ベースラインの確定

Phase 2 以降で追加するもの: フレーム横断照合、分類スコアリング（Phase 2）／マスク生成（Phase 3）／コンポジット合成（Phase 4）。

## 8. やらないこと

- **カバレッジ率の目標値を置かない。** 数値を追うと自作自演テストを誘発します
- **UI の自動テスト。** Large を増やすだけで割に合いません
- **プライベート関数の直接テスト。** 必要だと感じたらモジュール分割のサイン
- **PJSR オブジェクトのモックによるインタラクション検証**（4-2 参照）
- **検出性能をテストスイートに混ぜること**（5-1 参照）

## 9. SMURF による自己評価

| 軸 | 評価 | 備考 |
|---|---|---|
| **Speed** | 良 | Small が大半で秒オーダー。Medium は少数に限定 |
| **Maintainability** | 良 | 境界をプレーン配列に置き、PJSR への依存を局所化 |
| **Utilization** | **課題** | Medium は PixInsight が必要で CI に載らない。Small のみ CI 化を検討 |
| **Reliability** | 良 | 乱数は seed 固定。Medium を少数に保つ |
| **Fidelity** | **課題** | 合成フィクスチャは実データの複雑さ（薄雲、密集星野、レンズ収差）を再現しない。ここは 5 章の評価が補う |

Fidelity と Reliability のトレードオフを、**テスト（合成・決定的・高信頼）と評価（実データ・高忠実）を分離すること**で解いている構造です。
