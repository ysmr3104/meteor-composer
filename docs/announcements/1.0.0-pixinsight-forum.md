## Body (BBCode — copy from here)

```bbcode
Hello everyone,

I have released [B]MeteorComposer[/B], a script that walks through a whole night of registered frames, lists meteor candidates, lets you accept or reject each one at 1:1, and composites the accepted meteors onto a master light.

Repository URL (Resources > Updates > Manage Repositories):

[CODE]https://ysmrastro.github.io/pixinsight-scripts/[/CODE]

Requires [B]PixInsight 1.9.4 or later (V8 runtime)[/B]. No external dependencies: pure PJSR, no Python, no third-party processes. After installation it appears under [ICODE]Script > Image Analysis > MeteorComposer[/ICODE] and [ICODE]Script > ysmrastro > MeteorComposer[/ICODE].

[HEADING=2]Why I wrote it[/HEADING]

This need has come up on this forum before and never got an answer.

In August 2011, someone asked for a way to search roughly 600 files for meteors:

[QUOTE=twade]I'm looking for some software that will search my image files for meteors? It's pretty tedious manually looking through almost 600 files.[/QUOTE]

The suggestions were external programs for moving objects, and blinking. The thread ends with the question "Blinking over 600 images?".

[URL]https://pixinsight.com/forum/index.php?threads/meteor-detection-software.3189/[/URL]

In March 2025, another user tried to keep the meteors while removing the stars with StarNet2, and found that the meteors went away with the stars:

[QUOTE=jcschultz01]I have spent way too much time trying to remove the stars and leave the meteors.[/QUOTE]

[URL]https://pixinsight.com/forum/index.php?threads/meteor-detection.25389/[/URL]

I hit the same wall this August. I shot 654 frames of the Perseids, went through them in Lightroom, and found [B]9[/B] meteors by eye. It took a long time and I was not confident I had found them all. Screening the same data set with this script, I accepted [B]31[/B] — and all 9 of the ones I had found by eye were among the candidates it proposed.

[HEADING=2]What it does[/HEADING]

Four stages:

[LIST=1]
[*][B]Detection[/B] — scan every frame and build a list of meteor candidates
[*][B]Screening[/B] — present the candidates with previews so you decide on each one
[*][B]Mask generation[/B] — build a trail mask for each accepted candidate from its measured light distribution
[*][B]Composition[/B] — composite the accepted meteors onto a master light
[/LIST]

Screening is where the time goes, so that is where the work went. The selected candidate is always shown at 1:1, because a downscaled view cannot separate a meteor from a satellite. Verdicts are single keystrokes and are written to disk on every keystroke. Objects that travel along the same path across several frames — satellites and aircraft — are matched into tracks and can be hidden as a group. Candidates are scored and sortable, and there is a per-edge exclusion mask for landscape and streetlights.

[HEADING=2]Nothing is discarded automatically[/HEADING]

This is the design decision the whole thing is built around, so I want to state it plainly: [B]detection stops at proposing candidates, and the accept/reject decision always stays with the user.[/B] The classifier only reorders and optionally filters the list; by default it hides nothing.

The reason is asymmetry. A false positive costs one keystroke. A missed meteor is gone, and the user has no way to know it was ever there. So the classifier is never allowed to be the last word — for example, trail colour contributes to the score, but its weight is capped so that no candidate can be removed by colour alone.

[HEADING=2]No AI in the processing path[/HEADING]

I used AI extensively while developing this. [B]I deliberately used none of it in the processing path.[/B] The detector is background subtraction, a robust threshold, connected components, and second moments. The reason is reproducibility: I ran the same 654 frames twice and confirmed the candidate geometry and colour measurements were bit-identical, which is what makes it safe to re-run detection after screening without losing the verdicts already recorded.

[HEADING=2]Measured on my data set[/HEADING]

654 frames, ILCE-7M3 with a 20 mm lens on a tracking mount, 13 s exposures, 6024x4024, registered by WBPP.

[TABLE]
[TR][TH]Measurement[/TH][TH]Value[/TH][/TR]
[TR][TD]Candidates detected[/TD][TD]360[/TD][/TR]
[TR][TD]Visually confirmed meteors recovered[/TD][TD]9 / 9[/TD][/TR]
[TR][TD]Detection time[/TD][TD]~9 min (810 ms per frame)[/TD][/TR]
[TR][TD]Pixels changed outside the mask during composition[/TD][TD]0[/TD][/TR]
[/TABLE]

[HEADING=2]What I would like help with[/HEADING]

[B]My validation set is one night, one sky, one camera, one shower.[/B] The parameters are tuned against that, and I have no idea how they behave elsewhere. I would be glad to hear about:

[LIST]
[*]brighter skies
[*]other focal lengths, where the expected trail length changes
[*]fixed-tripod sequences
[*]other showers, with different entry speeds and colours
[/LIST]

The most useful report is "this meteor never showed up as a candidate". "This obvious artefact scored near the top" is equally welcome.

Source code and issue tracker (MIT licence):
[URL]https://github.com/ysmr3104/meteor-composer[/URL]

Documentation:
[URL]https://ysmrastro.github.io/pixinsight-repository/meteor-composer/en/[/URL]

Thanks for reading.
```

## 日本語訳（内容確認用）

**投稿するのは上の BBCode です。** これは内容を確認するための訳です。

### スレッドタイトル

> MeteorComposer — 一晩分のフレームから流星を検出し、目で選別して、採用したものを合成する

### 本文

みなさん、こんにちは。

**MeteorComposer** を公開しました。一晩分の registered フレームを走査して流星候補を列挙し、1 件ずつ原寸（1:1）で採否を決めさせ、採用した流星を master light に合成するスクリプトです。

リポジトリ URL（Resources > Updates > Manage Repositories）:

```
https://ysmrastro.github.io/pixinsight-scripts/
```

**PixInsight 1.9.4 以降（V8 ランタイム）が必要**です。外部依存はありません。純粋な PJSR のみで、Python もサードパーティ製プロセスも使いません。インストール後は `Script > Image Analysis > MeteorComposer` と `Script > ysmrastro > MeteorComposer` に出ます。

#### なぜ作ったのか

この要望は以前からこのフォーラムに出ていて、答えが出たことがありません。

2011 年 8 月、600 ファイルほどから流星を探す方法はないかという質問がありました。

> 画像ファイルから流星を探してくれるソフトを探しています。600 枚近くを手で見ていくのはかなり退屈です。（twade）

返ってきたのは移動天体向けの外部ソフトと、Blink でした。スレッドは「600 枚を Blink するんですか？」という問いで終わっています。

2025 年 3 月には、別の方が StarNet2 で星を消しつつ流星を残そうとして、流星も星と一緒に消えてしまうことに気づいています。

> 星を消して流星を残そうとして、時間を使いすぎました。（jcschultz01）

私も今年の 8 月に同じ壁に当たりました。ペルセウス座流星群を 654 枚撮り、Lightroom で 1 枚ずつ見て、目で見つけられたのは **9 個**でした。時間がかかったうえに、全部見つけられた自信もありませんでした。同じデータをこのスクリプトで選別したところ、**31 個**を採用しました。しかも目で見つけた 9 個は、9 個ともこのスクリプトが提示した候補の中に入っていました。

#### 何をするのか

4 段階です。

1. **検出** — 全フレームを走査して流星候補のリストを作る
2. **選別** — 候補をプレビュー付きで提示し、1 件ずつ判断させる
3. **マスク生成** — 採用した候補について、実測した光の分布から流星痕マスクを作る
4. **合成** — 採用した流星を master light に合成する

時間がかかるのは選別なので、手をかけたのもそこです。選択中の候補は常に 1:1 で表示します。縮小表示では流星と衛星を区別できないからです。判定はキー 1 打で、打つたびにディスクへ書き出されます。複数フレームにわたって同じ経路を移動するもの（衛星と飛行機）は軌跡として照合し、まとめて隠せます。候補はスコア付きで並べ替えられ、地上景や街灯のために辺ごとの除外マスクを備えています。

#### 何も自動で捨てない

これは全体がその上に組み立てられている設計判断なので、はっきり書いておきます。**検出は候補を提示するところで止まり、採否の判断は常に利用者の側に残ります。** 分類器はリストを並べ替え、任意で絞り込むだけで、既定では何も隠しません。

理由は非対称性です。偽陽性の代償はキー 1 打です。見落とした流星は失われ、しかも利用者にはそれが存在したことを知る手立てがありません。ですから分類器に最終判断を渡すことは決してしません。たとえば流星痕の色はスコアに寄与しますが、色だけでは候補を落とせないように重みに上限をかけています。

#### 処理の経路に AI を使っていない

開発では AI をかなり使いました。**処理の経路には意図的に一切使っていません。** 検出器の中身は、背景減算、ロバストなしきい値、連結成分、二次モーメントです。理由は再現性です。同じ 654 フレームを 2 回通し、候補の幾何と色の測定値がビット単位で一致することを確認しました。これがあるから、選別のあとに検出をやり直しても、記録済みの判定を失わずに済みます。

#### 実測値

654 フレーム、ILCE-7M3 に 20mm レンズ、追尾撮影、13 秒露出、6024x4024、WBPP で位置合わせ済み。

| 測定項目 | 値 |
|---|---|
| 検出した候補 | 360 |
| 目視で確認した流星の回収 | 9 / 9 |
| 検出時間 | 約 9 分（810 ms / フレーム） |
| 合成時にマスク外で変化した画素 | 0 |

#### 手を貸してほしいこと

**私の検証データは、1 晩・1 つの空・1 台のカメラ・1 つの流星群だけです。** パラメータはそれに対して調整してあり、他の環境でどう振る舞うのかは分かりません。こういう報告をいただけると助かります。

- もっと明るい空
- 別の焦点距離（想定される流星痕の長さが変わる）
- 三脚固定の連続撮影
- 進入速度や色が異なる別の流星群

一番役に立つ報告は「この流星が候補に出てこなかった」です。「この明らかなアーティファクトが上位に来た」も同じくらい歓迎します。
