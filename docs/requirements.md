# MeteorComposer 機能要件

> ステータス: ドラフト（要件整理段階）
> 最終更新: 2026-08-16
> リポジトリ: `ysmr3104/meteor-composer` / スクリプト名: `MeteorComposer`

---

## 1. 目的

一眼カメラで撮影した流星群の連番画像から、流星が写ったフレームを自動検出し、人手によるスクリーニングを経て、最終的に流星群コンポジット画像を生成する PixInsight スクリプト。

既存の `atomcam-meteor-detector`（ATOM Cam の動画から流星検出する Python パイプライン）とは**別物**であり、検出ロジックの考え方を部分的に参考にするに留まる。入力が動画ではなく長時間露出の静止画連番であること、リアルタイム性が不要であること、WCS が利用できることから、アーキテクチャは共有しない。

### 既存資産との関係

| プロジェクト | 本プロジェクトとの関係 |
|---|---|
| `manual-image-solver` | **UI 部品を流用**（ImagePreviewControl、ソート可能 TreeBox、Settings API によるセッション保存、Export/Import） |
| `split-image-solver` | 広角非 rectilinear の知見。将来の WCS 連携（輻射点算出等）の基盤 |
| `atomcam-meteor-detector` | 検出パラメータの相場観、マスクによる領域除外の考え方を参考 |
| `pixinsight-scripts` | 配信リポジトリ。updates.xri への追加が必要 |

## 2. スコープ

### 対象に含む

- 一眼カメラ（フルサイズ / APS-C）で撮影した流星群の連番画像
- 赤道儀による追尾撮影
- 三脚による固定撮影（**NPF ルールを遵守し、星が点像に写っているもの**）
- WBPP で位置合わせ・デベイヤーまで済んだ registered 画像を入力とする

### 対象に含まない

- 星が線状に流れるレベルの固定撮影（NPF を大きく逸脱したもの）。StarAlignment が通らないため対象外とする
- 動画からの検出
- リアルタイム検出
- 電波観測・複数地点観測との連携

### 実装方針の制約

- **PJSR ネイティブで完結させる**。配布容易性のため、Python・外部プロセス・サードパーティ製プロセスに依存しない（`manual-image-solver` と同方針）
- ES5 スタイル（`var` のみ、アロー関数・テンプレートリテラル不可）
- V8 エンジン前提（`CoreApplication.processEvents()`、`TextAlignment.*` 等のクラス静的定数形式）
- コード・コメント・コンソール出力・UI テキストはすべて英語

## 3. 入力データの前提

### 3.1 入力ファイル

WBPP が出力する **registered 画像**（`<output>/registered/` 配下）。キャリブレーション済み・コズメティック補正済み・デベイヤー済み・位置合わせ済みの状態。

registered を入力とする理由:

| 段階 | 可否 | 理由 |
|---|---|---|
| 元 RAW | × | ホットピクセル・カラム欠陥・アンプグローが線状偽陽性の温床になる |
| calibrated / debayered（位置合わせ前） | × | 検出座標が最終コンポジットの座標系と一致せず、座標変換が必要になる |
| **registered** | **○** | コズメティック補正済みで偽陽性が少ない。検出座標がそのまま後段のマスク生成・コンポジットに直結する |
| master light（積分後） | × | 流星はリジェクションで既に除去されている |

registered ファイル名には元サブフレームのファイル名が保持されるため、「どの撮影サブに流星が写っているか」の追跡が可能。

#### ディレクトリ構成（実測・要対応）

WBPP は `registered/` の直下ではなく、**撮影パラメータごとのグループサブディレクトリ**に出力する。

```
registered/
└── Light_BIN-1_6024x4024_EXPOSURE-13.00s_FILTER-NoFilter_RGB/
    ├── <元ファイル名>_d_r.xisf     ← 対象
    └── <元ファイル名>_d_r.xdrz     ← drizzle データ。対象外
```

- **`registered/*.xisf` の直下決め打ちでは 1 件も見つからない。** 再帰探索するか、グループを選択させる UI が必要
- **`.xdrz`（drizzle データ）が同じディレクトリに同居する。** 拡張子でのフィルタが必須。ファイル数は xisf の 2 倍に見える
- 露出やフィルタの異なる撮影が混在すると複数のグループができる。**複数グループを同時に扱うか、1 グループに限定するかは要決定**

ファイル名の変換は `<元ファイル名>` + `_d_r`（debayer + register）。元の JPG やサブと突き合わせる場合は、拡張子を除いた stem の前方一致で一意に決まる。

### 3.2 撮影条件の推奨範囲（固定撮影）

固定撮影では視野が 15°/時 で流れるため、StarAlignment が成立し、かつ実用的な重なり（70〜80%）を確保できる範囲に撮影時間を制限する必要がある。

以下はフルサイズ・F2.8・画素ピッチ 4.3µm（≒24MP）を仮定した目安。

| 焦点距離 | 水平画角 | 推奨撮影時間 | NPF 目安 | 概算枚数 |
|---|---|---|---|---|
| 14mm | 104° | 〜2 時間 | 約 16 秒 | 約 450 枚 |
| 24mm | 74° | 〜1.5 時間 | 約 10 秒 | 約 570 枚 |
| 35mm | 54° | 〜1 時間 | 約 7 秒 | 約 550 枚 |
| 50mm | 40° | 〜45 分 | 約 5 秒 | 約 600 枚 |

補足:

- **超広角側は重なり率ではなく StarAlignment の変換モデルが先に限界を迎える**。14mm で 30° 回転させると単純なホモグラフィでは周辺が合わない。ドキュメントで distortion correction（スプライン）の有効化を案内すること
- NPF 遵守＝短時間露出のため、**どの焦点距離でも一晩の枚数は 500〜600 枚に収束する**。1 枚あたりの処理時間予算がそのまま総処理時間を決める

### 3.3 registered 固有の注意点

1. **WBPP は整列に失敗したサブを registered に出力しない**。雲・振動で落ちたフレームに流星が写っていても検知できない。スクリプトは「入力サブ数 N / registered M / 未検査 N−M 枚」を明示的に警告すること
2. **無効領域（ゼロ埋め）が参照フレームからの時間差に比例して増える**。固定撮影では顕著。検出時に除外し、コンポジット時には全フレーム共通の有効域を提示すること
3. **補間リンギング**。StarAlignment の Lanczos overshoot により明るい星の周囲に正負のリングが残る

## 4. 検出アルゴリズム

### 4.1 方式の選択：単フレーム線検出

**参照差分方式（対象フレームから参照画像を引いて残差で検出する方式）は採用しない。**

参照差分には以下の 3 通りがあるが、いずれも本用途では割に合わない。

| 参照の作り方 | 呼称 | 備考 |
|---|---|---|
| 前後の隣接フレーム | 隣接フレーム差分 | `atomcam-meteor-detector` の方式 |
| 前後 ±N 枚の中央値 | ローリング中央値差分 | 隣接差分より頑健 |
| 全フレーム中央値 / master light | マスター差分 | 参照の S/N が最も高い |

**不採用の理由:**

- 参照差分が消してくれるのは星と静的構造だが、そこは伸長比フィルタで自明に落ちる（星は伸長比 ≒1、流星は数十以上）
- **本当に難しいのは衛星・飛行機の除外であり、これらは transient なので差分では消えない**。難しい問題に効かない
- **固定撮影で地上景が入ると破綻する**。registered 座標系では地上物が動くため、master light に地上物が流れて写り、差分すると輪郭が巨大な残差になる
- master light の存在が前提となり、WBPP を最後まで回さないと検出が始められない

**採用する方式：registered 1 枚の中だけで完結する線検出。**

```
背景除去（大スケール成分のモデルを引く）
  → 閾値化（残差の MAD から kσ）
  → 連結成分ラベリング
  → 各ブロブの 2 次モーメント → 伸長比・方位角・長さ・始終点
```

参照画像を作らず、前後フレームも読まないため、500 枚を 1 枚ずつ読み捨てられる。メモリ・I/O とも最小。

参照差分は、判定が微妙な候補に対する second opinion として**任意適用のオプション**に留める。

### 4.2 星と流星の分離根拠

24mm フルサイズ（6000px 幅、水平 74°）で 1px ≒ 0.74 分角。

| | 星 | 流星 |
|---|---|---|
| 形状 | 円形、FWHM 2〜5px | 直線 |
| 長さ | — | 1° の短いものでも約 80px、5° なら約 400px |
| 伸長比 | ≒1 | 数十〜数百 |

分離マージンは極めて大きく、参照差分に頼る必要がない。

**星の実測伸長比を基準にする。** `StarDetector` から得た星の伸長比を測定し、固定閾値ではなく「星の伸長比の N 倍以上」を判定条件とする。これにより「NPF をある程度遵守」レベルの軽微な追尾ズレにも自動追従する。

### 4.3 2 パス構成

```
1st pass（全 500 枚 / 1/8 縮小）
  輝度抽出 → 縮小 → 背景除去 → マスク適用 → 閾値 → 連結成分 → 伸長比
  星処理なし。安く広く拾う

2nd pass（1st を通過した数枚 / 原寸）
  StarDetector → 星・回折スパイク棄却 → 共線マージ
  → 始終点座標・長さ・方位角・輝度プロファイル抽出

3rd pass（候補リスト上のみ、画像読み込み不要）
  フレーム横断の候補照合 → 衛星・飛行機の判定
```

**ダウンサンプルは線状天体にとって不利にならない。** 1/8 に落とすと流星の輝度コントラストは約 2.7 倍下がるが、ノイズは 8 倍下がるため S/N はむしろ約 3 倍改善する（線に沿ったビニングに相当）。一晩の流星は数本〜数十本なので、2nd pass の対象は数枚に収まり、実質コストは 1st pass のみ。

### 4.4 背景除去

大スケールの明るさムラ（光害、月明かり、天の川、周辺減光の残り）を除去し、閾値を 1 本の値で決められるようにする。

採用手法は**強くダウンサンプルして元サイズに戻し、差分を取る**方式。

```
検出用画像 (750×500)
  → さらに 1/8 に縮小 (94×63)   ← 細い線が消え、背景だけが残る
  → 750×500 に拡大し戻す         ← 背景モデル
  → 検出用画像 − 背景モデル       ← 平坦化された残差
```

- 縮小時に median を使えば、流星や星がモデルに混入しない
- 既に 1/8 に落とした画像上で走るためコストはほぼゼロ
- ABE や MultiscaleLinearTransform は 500 枚に対しては過剰

### 4.5 閾値決定

平坦化された残差の MAD から `k × 1.4826 × MAD` で自動決定する。流星が占める画素は全体のごく一部のため、MAD は流星に汚染されない。

`k` をユーザー向けの主要な感度パラメータとして公開する。

### 4.6 星起因の偽陽性への対処（2nd pass）

伸長比だけでは落ちない、星に起因する偽陽性を潰す。

1. **回折スパイク** — 絞った明るい星から伸びる十字の光条。本物の直線なので形状では区別できない
2. **密集星野での星の連結** — 天の川では閾値化した星同士が隣接して数珠つなぎになり、細長い塊になる
3. 飽和星のブルーミング、レンズゴースト、ハロー

`StarDetector`（PJSR ネイティブの C++ オブジェクト。StarAlignment が内部で使うのと同じもの）で星の位置・明るさ・サイズを取得し、以下を適用する。

- **星の領域をゼロにしてはならない。** 流星が星の上を通過している場合、そこで途切れて 2 本の短い線に分断される
- 連結成分とモーメントを取った**後**に、候補の重心が検出済みの星と一致すれば星として棄却
- 線状候補の中心が明るい星の位置と数 px 以内で一致すれば回折スパイクとして棄却
- 分断された候補は**共線マージ**（同一直線上の断片を 1 本に統合）してから評価する

**1st pass では星マスクは不要。** 1/8 に落とすと FWHM 3px の星は 0.4px となりノイズフロアに埋もれる。密集星野の連結も縮小平均でなだらかな背景に変わり、背景除去で落ちる。縮小自体が星除去として機能する。

#### 実例: 静止した偽陽性を確認（2026-08-17、要調査）

**上記「1st pass では星マスクは不要」は、実データでは成立していなかった。** スクリーニング UI で最初に候補をめくったときに見つかった。

DSC04964〜04968 の連続フレームで、同じ位置に同じ候補が出る。ユーザーの目視では**飛行機でも衛星でもない、ただの星空**。

| フレーム | cx | cy | 長さ | 角度 | 伸長比 | 画素数 |
|---|---|---|---|---|---|---|
| DSC04964 | 421.9 | 180.9 | 14.1 | 86.5 | 6.1 | 20 |
| DSC04965 | 421.9 | 180.8 | 14.1 | 85.8 | 6.0 | 22 |
| DSC04966 | 421.9 | 180.9 | 14.1 | 86.5 | 6.1 | 20 |
| DSC04968 | 421.9 | 180.9 | 14.1 | 86.5 | 6.1 | 20 |

**重心が 0.1 サンプル以内で一致し、長さ・角度・画素数までほぼ同一。** 衛星や飛行機は動くので、これは動かないもの、すなわち registered 座標系で静止しているもの＝**恒星起因**である。伸長比 6.1 は閾値 6.0 のすぐ上で、4.2 の「伸長比は流星と衛星を分離しない」という実測とも符合する。

ここから読み取れること:

1. **「1/8 縮小が星除去として機能する」は言い過ぎだった。** 密集した星の連なりや回折スパイクは縮小後も残りうる
2. **静止性は衛星判定とは別の、より鋭い判別軸になる。** 現在の `matchAcrossFrames` は `maxCentroidShift = 400` と緩いためこの 4 本も 1 本の軌跡にまとまり `persistent` として落ちるが、それは「衛星だから」という誤った理由で落としている。**流星は 1〜2 フレーム、衛星は滑らかに移動、恒星起因は不動**の 3 分類のほうが実態に合う
3. 不動判定は既存データだけで実装できる（画像の再読み込み不要）

**出現数を全フレームで数え直した（2026-08-17 追記）。** 当初 5 枚と見えていたが、`(421.9, 180.9)` の半径 3 サンプル以内に出る候補は **22 フレーム**あった。**全 411 候補の 5.4% が、この 1 箇所の固定構造に由来する。**22 件はすべてスクリーニングで `not-meteor` と判定されている。

静止フィルタを入れれば、この 1 箇所だけで候補が 5% 減る。他にも同種の構造があれば効果はさらに大きい。

**未調査の点**（10 章の未決事項にも記載）:

- この位置に実際に何が写っているのか（密集星野か、回折スパイクか、ゴーストか）。原寸で確認する
- 他に同種の静止構造がいくつあるのか。上記は 1 箇所を数えたにすぎない
- 静止判定の閾値（何サンプル以内の移動を「不動」とみなすか）。実測では重心のばらつきが 0.1 サンプル以内なので、余裕をみても数サンプルで足りる

#### 判定が際どかった 1 件（2026-08-17）

`DSC04908 #1` は `meteor` としたが、**31 件の中で唯一、3 つの検出閾値すべてにほとんど余裕が無い**。

```
len 11.2 (最小 10.0)   elong 6.4 (最小 6.0)   px 14 (最小 12)
```

判断材料は次のとおり。

- **完全に孤立している。** 654 枚全体で、この位置の半径 60 サンプル以内に他の候補は 1 件も無い。衛星・飛行機・静止構造のいずれでもない
- 同じフレームの `#0` は角度 64 度前後で連続移動する明確な衛星軌跡（DSC04904〜04914）であり、`#1` とは無関係
- 目視では**軌跡両端の輝度の薄まり方**から流星と判断された。これは 6.1 が挙げている輝度プロファイル（増光→減光、非対称）そのもので、**表にはあるが未実装の特徴量が人手では実際に機能した**という証拠になる
- **輻射点から出ていないため、この日のペルセウス座流星群由来ではない**（散在流星の可能性）

**`meteor` のまま残す。** 散在流星も流星であり、検出できるべき対象だからである。「輻射点を通らない＝流星でない」ではない（6.1.1）。

**ラベル（流星か否か）と採否（コンポジットに採用するか）は別の軸である。** 群のコンポジットを作る際に群外を外すのは Stage 3/4 の選択の話であって、正解ラベルの話ではない。正解データは検出性能を測るためのものなので、散在流星を除外すると測るべきものが測れなくなる。

## 5. 検出対象エリアの除外

### 5.1 前提：registered 座標系では地上線が回転する

- **赤道儀追尾** — カメラが星を追うため生フレーム上で地上が動く。registered ≒ 生フレーム座標なので、地上線は傾いているうえに回転する
- **固定撮影** — 生フレーム上では地上は静止するが、星基準に揃えた registered 座標では地上が回転する

**どちらの撮影方式でも、registered 上の地上線は一晩を通して同じ位置に留まらない。** 回転量は向きと緯度に依存し、南中付近を向いていると速く、天の北極付近なら遅い。1〜2 時間で数十度変わることもある。

`atomcam-meteor-detector` の「下部 15% を除外」という固定値が成立していたのは、ATOM Cam が固定でカメラ座標のまま処理していたため。本プロジェクトでは座標系が異なる。

### 5.2 3 段構成

**Tier 1 — 静的な半平面**（優先度：高）

回転可能な直線 1 本で画面を二分し、片側を除外。パラメータは `角度 θ` と `オフセット d`。短時間セッション、または余裕を持ってマスクする運用ならこれで足りる。

**Tier 2 — キーフレーム補間**（優先度：高）

先頭フレームと末尾フレームで直線を設定し、間はタイムスタンプで線形補間。回転に追従でき、WCS も撮影地情報も不要。実装コストが低い割に効果が大きい。

**Tier 3 — WCS からの自動地平線算出**（優先度：中）

プレートソルブ済みなら各ピクセルの赤経赤緯が分かるため、`DATE-OBS` と観測地の緯度経度から全ピクセルの高度角を計算し、指定高度以下を自動除外する。フレーム毎に厳密に追従する。既存の solver 資産が活きる部分。

ただし **Tier 3 が消せるのは幾何学的な地平線のみ**で、地平線より上に突き出す木や建物は消せない。Tier 3 を実装しても Tier 1/2 の手動マスクは併用が必要。

### 5.3 形状

実際の風景は「左に木立、右に建物、下に地面」のように複数方向から張り出す。

- **回転可能な半平面を複数本、AND / OR で組み合わせる**（優先度：高）— 実装が軽く、多くのケースをカバーできる
- **マスク画像の読み込み**（優先度：中）— 任意形状の逃げ道。`atomcam-meteor-detector` に既存の機能
- 多角形指定（優先度：低）— より自由だが UI コストが高い

### 5.4 実装上の必須事項

**除外領域は「検出しない」だけでなく、統計計算からも外さなければならない。**

- **MAD 計算より前にマスクを適用する。** 明るい地上景（街灯、ライトアップされた建物）が統計に入ると MAD が引き上げられ、空側の検出感度が丸ごと落ちる
- **背景モデル生成時にも地上を除外する。** 含めると空側の背景推定が歪む

この処理順序は間違えやすいので、実装時・レビュー時のチェック項目とする。

### 5.5 UI

`manual-image-solver` の `ImagePreviewControl` を流用する。

- プレビュー上に直線をオーバーレイ描画し、除外側を半透明でシェーディング
- ドラッグで直線を操作（既存のクリック / ドラッグ判別ロジックを流用）
- 角度・オフセットの数値入力も併設
- **除外面積の実測値を表示**（例：「除外領域が画面の 32% を占めています」）。マスクし過ぎに気付けるようにする

### 5.6 registered のデータが無い領域（2026-08-18）

**WBPP は registered フレームを固定キャンバスに書くため、位置合わせではみ出した部分に何も無い（厳密なゼロ）領域ができる。仕様上避けられない。** どのフレームにも数サンプル幅の帯が片側にあり、あるフレームでは斜めの楔が面の 38% を占めていた。

操作者から「縁で何かを検出している」「線としての長さがないものを検出している」として 6 件の報告があり、実測すると**全部同じ原因**だった。

| 報告 | 実測 | 正体 |
|---|---|---|
| 4932 / 4933 / 4944 | x = 3〜4（753 サンプル中）、角度 88〜90°、幅 1 サンプル | 画像の左端 |
| 4912 / 4913 | 角度 62〜65° の斜め、一方は y=0 から | 黒い楔の境界 |

**411 候補のうち 61 件（14.8%）が画像の縁 5 サンプル以内**、59 フレームに分布していた。

#### 原因は背景モデルの汚染

`removeBackground` は 8 サンプルのブロック中央値を引く。**境界に跨るブロックはゼロを含むので中央値が空とゼロの間に落ち、引きすぎた結果として空が正の残差として境界沿いに残る。** 直線検出器はそれを正しく直線として見つける。

`downsample` と `removeBackground` がマスクを受け取るようにし、データの無いサンプルを背景モデルとロバスト統計の両方から外した。**これだけで報告された 6 件は根元から消えた。**

#### 統計への影響は予想と逆だった

「黒い領域は median を下げるので閾値も下がり過敏になる」と予想して測ったところ**逆**だった。38% が空のフレームで、生の場の MAD は 6.50e-5 対 2.39e-5（空だけなら後者）。**2 つの集団の差を測っているのであって、どちらのノイズでもない。**

ただし**平坦化後**の場では話が逆転する。データ無し領域は平坦化すると厳密なゼロになり、同じ値が大量にあると MAD がゼロに寄る。DSC04908 では sigma が 1.67e-6（正しくは 4.28e-6）で、**閾値が 2.6 倍低かった。**

#### 素直な対策は使えない

**正解データの流星が縁から 4 px の所にあり、それは visual（recall のハードゲート）である。**

| 正解流星 | 由来 | 縁からの距離 |
|---|---|---|
| DSC05001 | **visual** | **4 px** |
| DSC05281 | screening | 4 px |
| DSC05338 | screening | 4 px |
| DSC05032 | **visual** | **44 px** |

縁から一律に除外すると 31 本中 6 本以上、visual 2 本を失う。**区別すべきは「縁の近く」ではなく「境界に沿っている」。**

候補の画素のうちデータ無し領域に隣接する割合（`edgeContact`）を検出時に測って記録する。実測で棄却したいもの **49〜100%**、残したい流星 **0〜5%** と完全に分離した。判定は分類器に任せ、閾値 0.30 を超えたらスコアを 0.02 倍にする。**棄却はしない**（4.6 で星に対して採ったのと同じ形: 領域を先に潰さず、連結成分を取った後に候補ごとに判定する）。

#### 結果

| 項目 | 修正前 | 修正後 |
|---|---|---|
| 候補総数 | 411 | **376** |
| 報告された 6 件 | 検出 | **全部消滅** |
| 縁 5 サンプル以内 | 61 | 34 |
| `edgeContact ≥ 0.30` | — | 3 件 |
| **正解流星で誤って落ちるもの** | — | **0 本** |
| **visual recall** | 9/9 | **9/9** |

#### 実装でつまずいた 2 点（どちらもテストが自分の思い込みに同意していた）

**「データが無い」の条件。** 最初 `!(v > 0)` と書いたところ既存テストが 3 件落ちた。背景を引いた空のノイズは半分が負なので、フィクスチャの半分を「データ無し」と判定していた。WBPP が書くのは厳密なゼロであり、64 画素を平均したサンプルも厳密にゼロになる。**ノイズが厳密にゼロになることはまず無い。** `v === 0` または非有限に限定した。あわせて場の過半がゼロなら適用しない（穴の空いたフレームのための機能であり、ほぼ全部がゼロの場は別物）。

**`edgeContact` が画素の表現を取り違えていた。** `connectedComponents` が返すのは `{x, y, w}` のオブジェクトでインデックスではない。`pixels[i] % width` が `NaN` になり `usable[NaN]` が `undefined` = 偽 になるので、**全候補の全画素が「データ無しに隣接」と判定されていた。正解流星 31 本中 13 本（visual 3 本を含む）が誤って落ちる状態だった。**

**単体テストは通っていた。** 自分の誤った前提のまま、テスト側もインデックス配列を渡していたためである。**捕まえたのは正解データとの突き合わせだけだった。** DSC05196 以前が 100%、DSC05277 以降が 0% という時刻での分割が手掛かりで、幾何的な理由ではありえないと分かった。テストは `connectedComponents` の出力を使うように書き換えた。**実際の生産者から画素を取ることで、片方の思い込みではなくインターフェースを検査することになる。**

#### DSC04908 の喪失を受け入れた

統計を正した結果、DSC04908 の候補が消えた（screening 由来 22 本中 1 本）。**recall 低下は規約上「即 NG」だが、2026-08-18 に受け入れると判断した。**

- 旧コードの sigma 1.67e-6 は**バグによる異常値**で、この候補はその低い閾値のおかげで検出されていた。検出能力の損失ではなく、事故が起きなくなった
- **visual recall は 9/9 のまま**（ハードゲートは無傷）
- このフレームはフィットのスケール 0.097 でコンポジットから以前から除外されており、**成果物には元々入らない**

`evaluate.js` に `--accept-regression="理由"` を追加した。理由は必須で、受け入れた回帰は前後の値・失ったラベル名とともに `baseline.json` に記録される。**そうしないとファイルには 30 と書かれるだけで、なぜ 30 なのか誰にも分からなくなる。**

### 5.7 Tier 1 の実装（2026-08-18 / 2026-08-19 に入力方式を変更）

**UI・幾何・検出への受け渡しまでを実装した。固定撮影の実データでの検証は未了**（データ待ち）。

#### 入力の形：辺ごとに「深さ + 傾き」

操作者が半平面の式を書くことはない。書くのは**辺ごとに「食い込み量（%）」と「傾き（度）」**で、これは風景の張り出しを口で言うときの形そのもの（「地面が下 1 割、少し傾いてる」）。傾きは**辺の中央を軸**に回る。

**傾きが 0 でなければ、深さが 0% でも辺の一部だけを覆える。** 中央を軸に回すので、深さ 0% + 傾きは「辺の中央から角までの三角形」になる。角を落とす形はこれで作る。

##### 両端の深さ方式を試して撤回した（2026-08-19）

PJSR の `SpinBox` が負の値を持てない（`setRange(-45, 45)` でも `min` は 0 になり、例外も警告も出ない）ため、一度**辺の両端での食い込み量**という非負 2 値の形に変更した。**これは撤回した。厳密に表現力が落ちるためである。**

両端の深さがどちらも 0 以上だと、境界線はその辺を横切ることができない。したがって**バンドは必ず辺を端から端まで覆う**。実際に操作者が必要としたマスク（境界が上辺の 25% 地点から抜け、左辺の 83% 地点から抜ける角の三角形）は、

- **深さ + 傾き**なら `Left: 10%, tilt +24` で表現できる
- **両端の深さ**では左辺の下端側が **−5.1%** になり、表現できない

**「半平面では辺の一部だけを覆えない」という判断は誤りだった。** 半平面とフレームの交わりは、境界が隣り合う 2 辺を抜けるときは三角形になる。1 本の直線が必ず端から端まで切るわけではない。

したがって傾きは**符号付きのまま**にし、SpinBox が制約する符号の部分だけを **`CCW` チェックボックス**に分離した（操作者の提案）。既定は未チェック＝時計回り＝正で、上記のケースがそれにあたる。

#### 配置

| 決定 | 内容 | 理由 |
|---|---|---|
| 配置 | `Source / Destination` 内、**`Output` の下** | `Frames` と `Output` は「どこから読むか／どこへ書くか」の対。間に挟むと対が切れる。マスクはパスではなく検出設定なので `Run detection` の近くが自然 |
| 行数 | **辺は 2 行 × 2 辺、画像は 1 行** | 深さ + 傾き + 方向で 1 セル 231 px、4 セルを 1 行に置くと 1330 px で、ダイアログ最小幅で使える 1152 px を **178 px 超える**。2 行なら 634 / 816 px で収まり、除外率の表示も詳しく書ける（`tests/pjsr/probe_layout.js` で実測）|
| マスク画像 | **黒＝除外**（輝度 50% 未満） | 塗ったところが消えるという直感に合う |
| 併用 | **ラジオで排他** | 2 系統が同時に効くと、影がどちらに由来するのか UI のどこを読んでも分からない |

#### オーバーレイは「マスクそのもの」

除外範囲のシェーディングは、**数値から線を描き直すのではなく、検出が実際に受け取る配列から作る**。したがって表示と挙動が食い違うことが原理的に起こらない。1/8 グリッドなのでブロック状に見えるが、それは描画の粗さではなく**除外の粒度そのもの**（検出は 1/8 場で動く）。

- マスク変更のたびに `buildMask` → `maskRuns` → `Bitmap.fill` で行ラン単位に塗る。1 画素ずつ書かないので入力に追従する
- フレームと同じ矩形に `drawScaledBitmap` するので、ズーム・パン・回転に自動で追従する
- **除外面積の実測値を常に表示する**（`Excluded: 12.3%`）。これが無いと、マスクし過ぎは「検出数が減った」としてしか現れず、静かに recall を壊す。ラベルには固定幅を与えている（数字が伸びて隣のスピンボックスを押し出さないため）ので、**そこに入り得る全ての文字列を測ってから幅を決める**

#### 何も設定しなければ何も変わらない

既定は `Edges` の全項目ゼロで、その場合 `maskForField()` は **`null` を返す**。`detectCandidates(field, options, null)` は Mask 行が存在しなかったときと完全に同じ経路を通る。全 1 のマスクを渡しても算術的には等価だが、「等価」は主張であって、わざわざ主張する理由がない。

#### フレームは Frames を選んだ時点で出す

マスクは隠す空を見ながら決めるもので、想像で決めるものではない。**`Frames` を選んだ時点で 1 枚目をプレビューに表示する。** 8 分の検出を回すまで画面に何も出ないのでは、マスクの入力ができない。

起動時（Settings に frames が残っている場合）は `onShow` から出す。コンストラクタでやるとウィンドウが出る前に約 1 秒止まり、ハングと区別がつかない。

#### 記録と永続化

- マスク指定を `detection_results.json` の `mask` に記録する。**これが無いと、候補リストと「画面の 1/3 を除外して得た候補リスト」がディスク上で区別できない**
- 結果を読み込むと、その結果が作られたときのマスクに UI を戻す（オーバーレイが嘘をつかないため）
- Settings に保存する。マスクは夜ではなく**場所**を記述するので、次回も同じ木立が邪魔をする

#### マスク画像は「フレームの向き」で読まれる（2026-08-19）

**プレビューの回転は表示だけの設定で、マスク画像の解釈には効かない。** ところがプレビューの回転は Settings に保存されるので、操作者は**自分が選んでいない回転状態のビューに出くわす**ことがある。そこで見えているものに合わせてマスクを塗ると、回転分ずれる。実際にこれが起きて、操作者は macOS のプレビューでファイルを回して合わせた。

原因の切り分けは `tests/pjsr/probe_mask_orientation.js` で行った。リーダー直後・`loadMaskLuminance` 後・検出グリッド上の 3 点で黒がどの隅にあるかを四分割で測り、**3 点すべてで一致した**（つまり読み込み経路は回転も反転もしていない）。残る差はビューの回転だった。

対処:

- **`Turn:` を Image の行に置いた**（0 / 90 / 180 / 270 度、時計回り）。外部の画像エディタに戻らずに合わせられる。回転は読み込み直しではなく配列の回転で行い、指定は `detection_results.json` と Settings に記録する
- **プレビューが回っているときはフレーム名の後に `view turned 90 deg` と出す。** 回転していることが UI のどこにも出ていなかったのが、この罠が黙って成立した理由
- マスク画像の寸法とフレームの寸法をコンソールに出し、**縦横比が 2% 以上違えば警告する。** 形が違うマスクは引き伸ばして当てるので、水平に塗ったつもりの縁が斜めになるが、オーバーレイを見てもそれは分からない

#### 半平面で足りない場合

操作者の指摘: **隠したい対象が必ずしも辺の両端に接するとは限らない。** これは両端方式の限界ではなく**半平面そのものの限界**で、「深さ + 傾き」でも同じである（1 本の直線はフレームを端から端まで切る）。辺の一部だけを覆うことは原理的にできない。

逃げ道は 5.3 の設計どおり**マスク画像**である。したがって画像経路を使いやすくすること（上記の `Turn:`）が、多角形指定より優先度が高い。

#### 未了

- **固定撮影の実データでの検証**（Tier 1 が必要になるデータがまだ無い）
- 半平面を辺ごとに複数本、あるいは多角形指定（5.3 で優先度：低）
- プレビュー上でのドラッグ操作（5.5 に挙げた項目。数値入力とライブ反映で入力はできるので、優先度は下がった）
- Tier 2（キーフレーム補間）は `mask_geometry.js` に実装済みだが UI から到達できない

### 5.8 マスクは実測で recall を失う（2026-08-19）

**マスクを掛けた領域に本物の流星が入る。** 同じ夜のデータで実測した。

| マスク | 候補数 | visual recall | screening recall |
|---|---|---|---|
| なし | 376 | **9 / 9** | 21 / 22 |
| `Left 7%, tilt 20` | 323 | **9 / 9** | 15 / 22 |
| 手描きマスク画像（除外 10.3%） | 306 | **8 / 9**（DSC05409 喪失）| 14 / 22 |

**手描きマスクは visual 流星（ハードゲート）を 1 本落とした。** 欠落した 9 件の重心をマスクの境界と照合すると 6 件がマスクの内側にあり、そのうち 1 件が DSC05409 だった。

原因は「マスクが下手だった」ことではなく、**そもそも手でマスクを掛ける必要が無かった**ことである。registered のデータが無い領域は **5.6 の対応で自動的に、フレームごとに、形どおりに除外されている。** 直線 1 本ではその形に沿えないので、はみ出した分がそのまま空の損失になる。

対処として、`Run detection` の開始時にコンソールへ次を出す。

```
mask excludes 10.3% of the frame - 4.1% of it has no data anyway, 6.2% is sky.
** 6.2% of the frame is sky the detection will not search. ...
```

**除外率だけでは足りない。** マスクが覆うものには「もともとデータが無い部分」と「本物の空」の 2 種類があり、recall を失うのは後者だけである。両者を分けて出さないと、10.3% という数字からは何も判断できない。空の側が 2% を超えたら警告する。

### 5.9 Reset（2026-08-19）

PixInsight のプロセス／スクリプトにある全リセットに相当するボタンを下段に置いた。**設定・パス・読み込み済みの検出結果・判定のすべてを捨てて起動直後の状態に戻す。**

実際の作業（8 分の検出、一晩の判定）を捨てるので、**実行前に確認ダイアログを出し、何が失われるかを書く。** 判定が存在する場合はその件数を文面に含める（「reset」という語は「116 件の判定を捨てる」ようには聞こえないため）。未保存の判定があるかどうかも書き分ける。

## 6. 衛星・飛行機の除外

### 6.1 判別に用いる特徴量

| 特徴量 | 流星 | 衛星 | 飛行機 |
|---|---|---|---|
| **他フレームでの再出現** | **1〜2 フレーム**（下記） | 連続フレームに連続的に移動して出現 | 同左 |
| フレーム貫通 | 途中で始まり途中で終わる | 端から端まで貫くことが多い | 同左 |
| 輝度プロファイル | 増光→減光、非対称。爆発痕あり | ほぼ一定 | ストロボで等間隔の破線 |
| 色（OSC） | 白〜青緑 | 白 | 航法灯の赤 / 緑が混じる |
| 同一フレーム内の平行線 | 単独 | Starlink トレインは平行多数 | — |

**最も強力なのは「他フレームでの再出現」。** 衛星も飛行機も連続する複数フレームに写り、位置が滑らかに移動する。形状特徴より遥かに効く。

実装上は、画像の再読み込みは不要で、**各フレームから抽出済みの候補の座標リスト同士を突き合わせる**だけで完結する（3rd pass）。

#### 流星は 2 フレームにまたがりうる（重要）

流星の発光は 1 秒未満だが、**露出は連続している**。露出の切れ目に発生した流星は、前フレームの終わり際と次フレームの始まりに分かれて記録される。**2 フレームに写ることは異常ではなく正常**である。

したがって「2 フレーム以上に出現＝衛星」という判定は**誤りで、またぐ流星を棄却する**。

2026-08-12 セッションの実測でこれを確認した。

| | 軌跡の長さ |
|---|---|
| 正解の流星（DSC05443 / DSC05444） | **2 フレーム** |
| 同じフレームを横切る衛星 2 本 | **11 フレーム / 14 フレーム** |

軌跡長の分布は 1 フレーム 63 本、2 フレーム 23 本、3 フレーム以上 44 本で、境界は自然に 2 に落ちる。

**カットオフは「2 フレーム以下は流星の可能性を残す」とする**（`candidate_ops.js` の `maxMeteorFrames`）。1 フレームにすると要確認は 54 枚まで減るが、またぐ流星を落とす。2 フレームなら 94 枚（全体の 14%）で、またぐ流星が保持される。要件の「デフォルトは取りこぼさない側に振る」に従い後者を採る。

### 6.1.0 色の実測（2026-08-17）

6.1 の表は色を判別軸として挙げていたが、このデータで測ったことは一度も無かった。検出は `getLuminance()` の出力で走っており、**色情報はそもそも捨てている**。判定済みの 411 候補（meteor 31 / not-meteor 380）に対して `tests/pjsr/probe_colour.js` で実測した。

#### 色は分離する。しかも伸長比より強い

軌跡上の輝度ピーク位置で背景を差し引いた RGB を取り、`g / (r + g + b)` を求めた。

| | n | 最小 | p25 | 中央値 | p75 | 最大 |
|---|---|---|---|---|---|---|
| meteor | 31 | 0.414 | 0.479 | **0.539** | 0.586 | 0.622 |
| not-meteor | 378 | 0.220 | 0.421 | **0.458** | 0.473 | 0.575 |

単一閾値での分離性能（balanced accuracy、0.5 が偶然）:

| 特徴量 | 精度 | 備考 |
|---|---|---|
| **緑成分比** | **0.801** | 閾値 0.492 以上、感度 0.710、特異度 0.892 |
| 長さ | 0.586 | |
| ピーク輝度 | 0.581 | |
| **伸長比** | **0.540** | **現在の主力フィルタ** |

**緑成分比は、検出で主力にしている伸長比よりはっきり強い。** 4.2 の「伸長比は流星と衛星を分離しない」という実測と整合する。

ただし**ハードフィルタには使えない**。感度 0.710 は 31 本中 9 本を落とす。「デフォルトは取りこぼさない側に振る」（6.2）に反する。**総合スコアの一項として使う。**

数値は**同じデータで閾値を選んだ楽観的な上限**である。実運用ではこれより落ちる。

#### 絶対値で判定してはいけない

**`not-meteor` の中央値が 0.458 で、無彩色の 0.333 ではない。** 衛星は白いはずなので、この差はカメラ側の性質（Bayer 配列で緑画素が 2 倍ある等）を含んでいると考えるのが自然である。

したがって**比較対象は 0.333 ではなく母集団**であり、「0.4 を超えたら緑」のような絶対閾値は機材が変われば破綻する。**そのセッションの候補群の分布に対する相対位置**で評価すること。

#### 飽和仮説は検証できなかった（要追試）

スクリーニング時に「明るい流星は R と B も十分反応して白くなる」という仮説が出た。**このデータでは検証できない。**

```
peak channel（1.0 = クリップ）   meteor 最大 0.284 / not-meteor 最大 0.304
```

**全 411 候補でクリップに達しているものが 1 つも無い。** 仮に元データでクリップしていれば 3 チャンネルが同値になって比率が 0.333 に寄るはずだが、そうもなっていない。

ただし**向きは符合している**。

| 候補 | 緑成分比 | ピーク |
|---|---|---|
| DSC05069（白いと報告） | 0.414 | **0.284**（全流星で最大） |
| DSC05542（白いと報告） | 0.478 | 0.089 |
| DSC05070 | 0.442 | 0.027 |
| 緑が濃い流星（上位 5 本） | 0.61〜0.62 | 0.016〜0.032 |

最も明るい 1 本が最も緑が薄い。**明るいほど緑が薄まるという向き自体は当たっている**が、明るい帯域に入る流星が 1 本しかなく、傾向として主張できる段階ではない。**明るい流星を含む別データが要る。**

#### DSC05069 / DSC05070 は露出をまたいだ流星の実例

端点が一致する。

```
DSC05069 #1  (571,56) → (541,52)   角度 9.3    ← 露出の終わり際
DSC05070 #0  (541,53) → (516,47)   角度 12.3   ← 次の露出の始まり
```

`maxMeteorFrames = 2` が守っている当のケースであり、6.1 に挙げた DSC05443/05444 より明快な実例である。なお 05443/05444 は**同じ場所で短く淡くなっており**（画素数 54 → 20、伸長比 14 → 6.4）、またぎというより流星痕の残光の可能性がある。両者は現象として別かもしれない。

なお 05069 と 05070 はピークが 0.284 と 0.027 で 10 倍違う。前半に明るい部分が入ったということで、またぎの解釈と整合する。

### 6.1.1 輻射点との整合（将来。2026-08-17 提案）

**主要な流星群の輻射点を内蔵し、プレビュー上にマークを描く。** 輻射点が画角に入っている場合に、それがどこかを見ながら判断できる。

ただしこれは表示の便宜にとどまらない。**群流星は、軌跡を逆向きに延長すると輻射点を通る。** これは幾何学的な定義そのものであり、次の判別に使える。

| 対象 | 軌跡の延長線 |
|---|---|
| 群流星 | **輻射点を通る**（ペルセウス座流星群ならペルセウス座付近） |
| 散在流星 | 通らない |
| 衛星・飛行機 | 通らない（軌道と輻射点は無関係） |

6.1 の表にある特徴量はいずれも「動きの有無」に基づくもので、**1〜2 フレームしか写らない対象どうしを分離できない**。輻射点との整合は、単一フレームの候補 1 本だけで評価できる唯一の方向性の手がかりになる。

**必要なもの**: registered フレームの WCS。プレートソルブが要るが、**registered なので 1 枚解けば全フレームに同じ解が使える**。既存資産の `manual-image-solver` / `split-image-solver` がそのまま使える。広角なら後者。

**注意点**:

- **角度の許容幅は輻射点からの距離に依存する。** 輻射点のごく近くでは軌跡が短く方向が定まらないため、逆に判定できない
- **散在流星を捨ててはいけない。** 「輻射点を通らない＝流星でない」ではない。**通る場合に群流星である確度を上げる方向にのみ使う**。要件の「デフォルトは取りこぼさない側に振る」に従う
- 内蔵する輻射点は日付依存（輻射点は日々移動する）。`DATE-OBS` からの補正が要る

**位置づけ**: Phase 5（WCS 連携・測定機能）。Phase 1 の判断には影響しない。

### 6.1.2 分類器の実測（2026-08-17、Phase 2）

`javascript/classifier.js` を実装し、判定済みの 411 候補で測った（`tests/eval/evaluate_classifier.js`）。

#### 実装の過程で 2 つの誤りが見つかった

**1. 固定構造は軌跡照合では見つけられない。**

当初は `matchAcrossFrames` の軌跡から静止判定を導いていた。しかし照合器は `maxFrameGap = 2` で、**動くものを追うための道具**である。固定構造は動かないうえ規則的に出現するとは限らず、実例は 613 フレームに散らばる 22 回の出現で、**照合器はそのうち 8 回しか結び付けられなかった**。

セッション全体を通した位置クラスタリングに変更した。ただし**位置だけでは危険**で、半径 3 サンプル以内に本物の流星を含むクラスタが実在した。分けるのは形状である。

```
固定構造 (421.8, 181.2)   length 14.07〜14.13   ばらつき 0.4%
偶然重なった 3 件          length 13.4 / 20.1 / 21.4   ばらつき 44%
```

**2. `maxCentroidShift = 400` が流星を 2 本巻き込んでいた。**

753 サンプル幅の視野に対して 400 は半分以上で、無関係なものを繋いでいた。

| maxCentroidShift | 軌跡数 | persistent | 巻き込む流星 |
|---|---|---|---|
| **400**（旧既定） | 130 | 302 | **2** |
| 200 | 135 | 297 | 0 |
| **100**（新既定） | 146 | 282 | **0** |

抑制効果は 93% 残したまま、流星を落とさなくなる。衛星は 11〜14 フレームで視野を横切るので毎フレーム約 60 サンプル動く。100 は本来の用途には十分広い。

#### 修正後の性能

| | 修正前 | 修正後 |
|---|---|---|
| 固定構造の検出 | 8 件 | **28 件（2 構造）** |
| 流星の巻き込み | 2 本 | **0 本** |
| 無償で落とせる非流星 | 8 / 380（2.1%） | **315 / 380（82.9%）** |
| スコア順での流星の順位（中央値） | 57 / 411 | **16 / 411** |
| 上位 50 行に入る流星 | 14 / 31 | **25 / 31** |

「無償で落とせる」は**最も低いスコアの流星より下**を意味する。そこで切れば流星は 1 本も失われない。

| カットオフ | 流星 | 残る非流星 | リスト |
|---|---|---|---|
| 0.00 | 31 / 31 | 380 / 380 | 411 |
| 0.05 | 31 / 31 | 338 / 380 | 369 |
| 0.20 | 31 / 31 | 85 / 380 | **116** |
| 0.40 | 31 / 31 | 69 / 380 | 100 |
| 0.50 | **29 / 31** | 58 / 380 | 87 |

最も低いスコアの流星は 0.446 だった。**プリセットはこれよりかなり下に置いてある**（standard 0.05、strict 0.20）。一晩のデータから読み取った閾値はその晩に適合してしまうためで、間違えたときの損失も非対称である。

#### 色の寄与

色を使わない場合でも 295 / 380（77.6%）は落とせる。色を足すと 315（82.9%）に上がり、**順位の改善のほうが大きい**（中央値 59 → 16、上位 50 行の流星 14 → 25）。色は「落とす」より「上に持ち上げる」方向に効く。

#### 設計上の原則

- **何も棄却しない。** スコアは並べ替えと、絞りたい人が自分で線を引くためのもの。既定のプリセットは何も隠さない
- **固定構造と衛星を別扱いにする。** 固定構造を `persistent` として落とすと「衛星だから」という誤った理由になり、操作者が読む理由が嘘になる
- **色は順位で評価する。** 絶対閾値は機材が変わると破綻する（6.1.0）

### 6.1.3 見かけの速度が変わる飛行機（2026-08-19）

操作者の報告: **4977 / 4978 のような飛行機が Strict に残る。**

実測すると、その飛行機は**トラック 3 として 4970〜4976 の 7 フレームで正しく追跡されていた**（スコア 0.150 で Strict から落ちる）。ところが 4977 と 4978 で切れて、それぞれ長さ 1 の別トラックになり、**スコア 1.000 で Strict の先頭に並んでいた。**

```
4976  (380,271)-(314,279)   len 66   ang 173   track 3/7   score 0.150
4977  (500,255)-(397,269)   len 104  ang 173   track 5/1   score 1.000
4978  (637,239)-(610,240)   len 27   ang 174   track 6/1   score 1.000
```

原因は `maxCentroidShift = 100`。4976→4977 の重心移動は **102.3**（わずか 2.3 超過）、4977→4978 は **176**。**飛行機は近づくにつれ見かけの速度が上がり、軌跡も長くなるので、固定半径の円では追従できない。**

半径を広げるのは駄目である。それは以前 400 で試して**正解流星 2 本を巻き込んだ**（`maxCentroidShift` のコメント参照）。**流星 1 本の損失は飛行機 30 機を残すより高い**（6.2）。

#### 共線連続で繋ぐ

近さではなく「**新しい軌跡が古い軌跡の延長線上にあり、その端から続いているか**」で判定する。これは空を横切る被写体がすることであり、無関係な 2 本の軌跡がまずしないことである。

- 垂直方向のずれ: 4977 の直線から 4978 は **2.6 サンプル**、4976 の直線から 4977 は **0.69 サンプル**
- 端点間の隙間: 4976→4977 が **17 サンプル**、4977→4978 が **111 サンプル**

**垂直距離の検査は一方向でなければならない。** 新しい軌跡を古い軌跡の直線に対して測る。逆向きに測ると、方向がほとんど決まっていない短い新軌跡が不当に不利になる — 去っていく飛行機の最後のフレームがまさにそれで、逆向きだと **21 サンプル**ずれていると判定されて繋がらない。

#### 実測

正解データをゲートにして測った。

マスク無しでベースラインと一致する実行（候補 376、recall 30/31）で測った。

| 規則 | persistent | Strict に残る数 | 正解の検出 | 正解を persistent にした数 | 正解を Strict から落とした数 |
|---|---|---|---|---|---|
| 重心のみ（従来）| 250 | 100 | 30 / 31 | 0 | 0 |
| + 共線連続 | 258 | **92** | 30 / 31 | **0** | **0** |

問題の飛行機は `track 1` から **`track 11`** になり、スコア 1.000 → **0.150** で Strict から落ちる。

マスクを掛けた別の実行（候補 306）でも同じ方向に動いた（persistent 217 → 225、Strict 77 → 69、正解を persistent にした数 0）。

**垂直許容 4〜20 サンプル、隙間 150〜400 サンプルの全域で結果が動かなかった。** つまり判別しているのは基準そのもので、閾値ではない。採用値はその保守側の端（`maxContinuationPerp: 6`、`maxContinuationGap: 150`）。

**2 フレーム流星は守られる。** 露出境界にかかった流星も自分の直線を続けるので共線連続の条件を満たすが、歯止めは幾何ではなく**トラック長**（`maxMeteorFrames: 2`）である。

### 6.1.4 1 本の軌跡が断片に割れる（2026-08-19）

操作者の報告: **5171 / 5343 / 5447 の飛行機がまだ Strict に残る。**

3 件とも同じ形だった。**物体は正しく追跡されて抑制されているのに、同じフレームの中で軌跡が 2 つに割れ、トラックに乗らなかった断片が満点で残っていた。**

```
5171 [0] (376,111)-(307,121) ang 171.1  8 枚のトラック  score 0.150
5171 [1] (305,120)-(280,126) ang 171.2  1 枚            score 1.000  ← 残る
              [0] の終端から 2.2 サンプル、同じ角度

5447 [0] (83,86)-(119,91)   ang 5.8  1 枚            score 1.000  ← 残る
5447 [1] (121,91)-(134,93)  ang 4.8  8 枚のトラック  score 0.150
              [0] の終端から 2.0 サンプル

5345 [0] (722,85)-(650,86)  ang 179  5 枚のトラック  score 0.150
5345 [1] (748,83)-(723,83)  ang 177  1 枚            score 1.000  ← 残る
              （操作者が 5343 として報告した飛行機の同一軌跡）
```

原因は**閾値処理が画素単位である**こと。軌跡がどこかで閾値を下回れば（淡い区間、重なった星をマスクした跡）、連結成分は複数に分かれる。**操作者から見れば「明らかな飛行機が、何の理由も付かずリストの先頭にいる」状態になる。**

#### 対処：検出の中で共線断片を統合する

`candidate_ops.js` の **`mergeCollinear` は実装もテストも存在していたが、どこからも呼ばれていなかった。** `detectCandidates` の最後に配線した。

**使う場所ではなく検出の中で統合する。** そうしないと結果ファイルと画面が「何が見つかったか」について食い違う。

| | 候補数 | Strict | 正解の検出 | visual | 正解を抑制 | 3 件の飛行機 |
|---|---|---|---|---|---|---|
| 統合なし | 376 | 92 | 30 / 31 | **9 / 9** | 0 | **Strict に 3 件** |
| 統合あり | 360 | **73** | 30 / 31 | **9 / 9** | 0 | **なし** |

統合されたのは 16 件で、全件が「隙間 1〜2 サンプル・同じ角度・1 本の直線」だった。誤って別物を繋いだ組み合わせは無い。

#### 統合が落としていたフィールド

`combineGroup` は `edgeContact` / `minorLength` / `majorLength` / `bbox` を返していなかった。**フィールドの欠落は失敗しない。** 下流には `undefined` が届き、それを読む側は黙って何もしない。

**特に `edgeContact` が致命的だった。** 分類器はこれが閾値 0.30 以上のときスコアを落とす（5.6）が、`undefined >= 0.30` は false なので、**データ境界に沿った統合候補は満点のまま素通りする。** 引き継ぐよう修正した（`edgeContact` は最大値、`minorLength` も最大値、`majorLength` は統合後の長さ、`bbox` は和集合）。

#### 遅延 sibling 依存という罠

`detection_core.js` が `candidate_ops.js` に依存したことで、新しい失敗の形が生まれた。純粋モジュールは無条件に `require` できない（PJSR に `require` は無い）ので、次の形を使う。

```js
(typeof mergeCollinear === "function") ? { mergeCollinear: mergeCollinear }
                                       : require("./candidate_ops.js")
```

**sibling を `#include` していない PJSR スクリプトでは `require` の枝に入り、ReferenceError で落ちる。** しかも Process Console にしか出ない。実際 `run_detection.js`（評価データを作る当のスクリプト）を含む 3 本が該当していた。

`tests/ut/test_module_isolation.js` に静的検査を追加した。**遅延 `require` を持つモジュールを `#include` している PJSR スクリプトは、その sibling も `#include` していなければならない。** 検査は意図的に外して 3 本を検出することを確認済み。

### 6.1.5 ストロボの飛行機と、2 つの照合規則の到達距離（2026-08-19）

操作者の報告: **5337 の飛行機が Strict に残る。**

切り出して見ると、**赤い破線状の軌跡**だった。航空機の衝突防止灯が点滅するため、軌跡が連続した線ではなく点線になる。

実態はこうだった。

| フレーム | 検出 | 備考 |
|---|---|---|
| 5337 | (20,98)-(45,98) 25 サンプル | 破線が繋がって 1 成分になった |
| 5338 〜 5340 | **なし** | 画像には明瞭に写っている |
| 5341 〜 5345 | トラック 5 枚、score 0.150 | 正しく抑制されている |

5337 と 5341 の間が 4 フレーム空き、`maxFrameGap: 2` を超えるため繋がらず、**孤立した 5337 が満点で Strict の先頭に来ていた。**

#### なぜ 5338 で検出できないか（実測）

`tests/pjsr/probe_strobe.js` で測った。**閾値の問題ではなく足切りの問題だった。**

sigma は 5337 と 5338 で同一（4.17e-6 と 4.16e-6）。5338 の破線は成分としては存在するが、1 つ 1 つが **5〜7 画素・長さ 2〜4・伸長比 1.6〜3.0** で、`minPixels 12` / `minLength 10` / `minElongation 6` を個別に通らない。

統合（`mergeCollinear`）は足切りの**後**に走るので、これらは統合される前に捨てられている。

**足切りの前に統合する案は採らなかった。** 1 フレームに 4 画素以上の成分が 873 個あり、そのほとんどは丸い塊で**角度が意味を持たない**（伸長比 1.6 では向きは雑音）。角度で共線判定できないものを統合対象にすると、雑音同士を繋いで偽の軌跡を作る。

#### 2 つの照合規則に別々の到達距離を与える

照合には 2 つの規則がある。**近接**（重心が円の中）と**共線連続**（新しい軌跡が古い軌跡の延長線上）。これらが 1 つのフレーム間隔上限を共有していた。

**同じ到達距離を与えるべきではない。** 4 フレームの近接は直径 400 サンプルの円で、ほぼ何でも繋がる。4 フレームの共線連続は依然として同じ直線上にあることを要求する。

| 近接 | 連続 | Strict | 正解を抑制 |
|---|---|---|---|
| 2 | 2 | 73 | 0 |
| 2 | **4** | **62** | **0** |
| 2 | 5 | 62 | 0 |
| 2 | 6 | 59 | 2 |
| **4** | **4** | 57 | **1（DSC05318）** |

**両方を 4 に上げると正解流星を 1 本失うが、連続だけを上げると失わない。** これが分離の根拠そのものである。4 と 5 は同じ挙動で、6 から失い始めるので、4 は 2 段の余裕を持つ。

`maxContinuationPerp` は 6 → 10 にした。5337 の軌跡は 5341 の直線から **7 サンプル**離れており 6 では届かない。**8〜20 の全域で結果が同一**なので、その中央付近を採った。

採用値:

```js
maxFrameGap: 2                  // 近接
maxContinuationFrameGap: 4      // 共線連続
maxContinuationPerp: 10.0
```

visual recall 9/9、正解を抑制した数 0 を維持したまま **Strict が 73 → 62** になった。

### 6.1.6 色を実際に供給する（2026-08-19）

**6.1.0 で緑成分比を実測し、分類器に `colourWeight 0.7` の項まで実装してあったが、`row.colour` を誰も設定していなかったので一度も効いていなかった。** 配線した。

#### 純粋モジュールに切り出した

`trail_colour.js`。呼び出し側が `sampler(x, y, channel)` を渡す形にしたので、画像なしで幾何（軌跡に沿って歩く、横断して最も明るい点を探す、背景を両側から取る）を Small テストで押さえられる。

新しく測った値は 6.1.0 の probe をよく再現している。

| | n | 最小 | 中央値 | 最大 |
|---|---|---|---|---|
| meteor (visual) | 9 | 0.450 | 0.528 | 0.622 |
| meteor (screening) | 21 | 0.414 | 0.564 | 0.622 |
| not-meteor | 326 | 0.220 | 0.461 | 0.575 |

360 候補すべてで測定に成功した。

#### 緑に見えない流星は落ちない（3 つの仕組みで保証）

**これは操作者からの懸念であり、観察ではなく不変条件としてテストに固定した。**

1. **乗数に下限がある。** `score *= (1 - w) + w * rank` なので、順位が最下位でも `1 - w = 0.30` までしか下がらない。Strict の 0.20 を割れない。**`colourWeight` を 0.80 超に上げるとテストが 3 つ同時に落ちる**
2. **測定に失敗したら「色なし」になる。** 軌跡を見つけられなければ差分がゼロになり `greenFraction` が `null` を返すので、**項自体が適用されない。** 誤った色を当てられて不利になることがない
3. **絶対閾値ではなくセッション内の順位**（`rankOf`）。6.1.0 の「not-meteor の中央値が無彩色の 0.333 ではなく 0.458」という実測に基づく

実データでの確認:

```
最も緑でない流星   DSC05069  緑成分比 0.414  score 0.395   Strict に残る
visual の最小      DSC05443  緑成分比 0.450  score 0.497   Strict に残る
```

#### 効果：リストは短くならないが、並び順が良くなる

**リストは 62 件のまま変わらない。** これは設計どおりで、乗数の下限が閾値を割らない以上そうなる。

| | 上位 20 件 | 上位 30 件 | 中央順位 |
|---|---|---|---|
| 色なし | — | 17 / 30 | 29 位 / 88 |
| **色あり** | **18 / 30** | **22 / 30** | **16 位 / 88** |

**30 本の流星のうち 18 本が上位 20 件に入る。** 操作者は上から見ていくので、これは実作業時間に直接効く。

#### なぜリストを短くできないか（測定済み）

Strict 62 件の内訳は**正解流星 30 件・判定済み偽陽性 31 件**でほぼ半々。以下はすべて測って否定した。

- **閾値を上げる** — 0.05 から 0.50 まで振っても 62 件のまま。生き残る行は**全部ちょうど 1.000** の二極分布
- **形状の特徴量** — 長さ・伸長比・画素数・幅・`edgeContact`・角度、すべて分布が大きく重なる
- **トラック長** — 使い切っている。3 枚以上は全部抑制済みで、残りは両方とも 1〜2 枚。**露出境界にかかった流星が 2 枚になる**ので原理的に分けられない
- **照合の到達距離を伸ばす** — 残る 31 件は取りこぼした軌跡の続きではない。最も近い共線の抑制済みトラックでも 12 フレーム以上離れており、**流星側も同じ傾向**
- **色でハードに切る** — `colourWeight 0.9` / cutoff 0.5 なら偽陽性は 31 → 22 に減るが、**visual 1 本と screening 3 本を失う**

### 6.1.7 輝度プロファイルは分離しない（2026-08-19、否定結果）

**測って否定した。次に同じことを試さないために記録する。**

仮説: 流星は短時間の現象なので軌跡に沿って明るくなって消える形があり、衛星は 13 秒間ほぼ一定なので平坦、飛行機のストロボは周期的。したがって軌跡に沿った輝度の形が流星と衛星を分けるはず。

`tests/pjsr/probe_profile.js` で、ラベル付き 357 候補（visual 9 / screening 21 / not-meteor 327）の軌跡に沿って 40 点サンプルし、5 つの形状特徴量を測った。

| 特徴量 | balanced accuracy |
|---|---|
| **緑成分比**（6.1.0、比較用）| **0.801** |
| asymmetry（ピーク位置の偏り）| 0.636 |
| endRatio（両端 / ピーク）| 0.628 |
| 長さ（6.1.0、比較用）| 0.586 |
| flatness（標準偏差 / 平均）| 0.578 |
| peakRatio（ピーク / 平均）| 0.563 |
| zeroFraction（背景以下の割合）| 0.519 |

**最良でも 0.636 で、長さ（0.586）とほぼ変わらない。** しかもこれは同じデータで閾値を選んだ楽観的な上限である。

四分位を見れば分離していないことがはっきりする。`peakRatio` は visual 中央値 3.229、screening 4.356 に対し **not-meteor 中央値 4.002 が両者の間**にある。

#### なぜ外れたか

**閾値処理が既に形を削っていると考えられる。** 軌跡として検出されるのは閾値を超えた部分だけなので、流星の「明るくなって消える」裾は最初から切り落とされ、残るのは明るい部分＝平坦な区間になる。測ろうとした形は、検出の時点で失われていた。

#### 未検証の仮説（次に測るならこれ）

Strict に残る「衛星」は、**衛星のフレア**（回転する衛星の一瞬の反射）ではないか。フレアなら 1〜2 枚しか写らず持続も短く、**流星と物理的にほぼ同じ見え方**になる。だとすれば 1 フレーム内の特徴量では原理的に分けられない。

ただしフレアには流星に無いものがある。**軌道に沿った、検出閾値以下の淡い軌跡が前後のフレームに続いている**はずで、流星は消えるので何も残らない。1〜2 枚の候補について前後フレームの延長線上を検出閾値より下まで調べれば測れる。

### 6.2 パラメータ設計

**検出パラメータと分類パラメータは、いずれも UI から変更できるようにする。**

| 段階 | パラメータ | 役割 |
|---|---|---|
| 検出（4 章） | `k`（閾値のσ数） | どこまで淡い信号を拾うか |
| | `minElongation` | 星と線状天体の分離 |
| | `minPixels` / `minLength` | 宇宙線ヒット等の除外 |
| | `backgroundFactor` | 背景モデルのスケール |

| | 総合スコアのカットオフ | 通常操作。スライダー 1 本 |
| | `maxMeteorFrames` | またぐ流星を守る境界（6.1 参照） |

操作の階層は次のとおり。

- **通常操作** — プリセット 3 段階（緩い / 標準 / 厳しい）＋ カットオフスライダー 1 本
- **詳細設定** — 上表のすべてを個別に変更可能

**既定値は別途検討する（未決事項）。** 現在コードに入っている値（`k=5.0`、`minElongation=6.0`、`minPixels=12`、`minLength=10.0`）は最初の実データを通すために置いた暫定値であり、根拠のある数字ではない。実際に走らせて候補数と検出できる流星を見ながら決める性質のもので、机上では決まらない。

**デフォルトは「取りこぼさない側」に振る。** 後段に人間のスクリーニングが控えているため、飛行機が 30 本混じることより流星を 1 本落とすことの方が損失が大きい。厳しくしたいユーザーだけがスライダーを動かす設計とする。

なお正解データ作成モードでは、これらを運用値よりさらに緩めて走らせる（[docs/tests.md](tests.md) 5-2 参照）。運用値で検出できた候補だけから正解を作ると、正解が検出器の性能に縛られるため。

### 7.1 Stage 2 — スクリーニング UI

`manual-image-solver` の資産をほぼそのまま流用できる。

- **候補リスト** — ソート可能な TreeBox（`headerSorting = true`）。列は フレーム名 / 時刻 / 長さ / 方位角 / スコア / 分類 / 採否チェックボックス。スコア順ソートで上から確認できる
- **プレビュー** — `ImagePreviewControl`（ScrollBox、ズーム / パン、オートストレッチ）。検出した線をオーバーレイ描画
- **セッション保存・復元** — Settings API
- **Export / Import** — 候補リストの JSON 入出力

流用元は **`manual-image-solver` 2.0.0（V8 版）の `ImagePreviewControl`**。`class extends ScrollBox` で書かれており、ズーム / パン / クリック選択 / マーカー描画 / 表示回転を備える。そのまま使える。

#### プレビュー画像の生成にネイティブ API を使う（2026-08-17 調査）

**`manual-image-solver` の `createStretchedBitmap()` は流用しない。** 同関数は 2048×1365 の per-pixel ループで、1 フレームあたり `image.sample()` 3 回 + `bmp.setPixel()` 1 回 × 280 万回 ≒ 1100 万回の PJSR 呼び出しになる。プレートソルブは 1 枚を 1 回変換するだけなので成立していたが、**94〜291 枚をめくるスクリーニングでは支配的なコストになる。**

PJSR 公式リファレンス（`/Applications/PixInsight/doc/pjsr/objects/`）と同梱スクリプトを調査した結果、**必要な処理はすべてネイティブ API に存在した**。WBPP（`BPP-LNReferenceSelector.js:606`、`BPP-Helper.js:1133`）が同じ用途で使っている定型パターンをそのまま採る。

```js
var median = view.computeOrFetchProperty( "Median" );
var mad    = view.computeOrFetchProperty( "MAD" );
var stf    = view.image.computeAutoStretch( median, mad.map( function ( m ) { return 1.4826 * m; } ),
                                            -2.8, 0.25, false );
var image = new Image( view.image );
image.applyDisplayFunction( stf );
var bmp = image.render();
image.free();
```

| 自前実装（流用しない） | ネイティブ API |
|---|---|
| `computeAutoSTF()` | `Image.computeAutoStretch()` |
| `midtonesTransferFunction()` の per-pixel 適用 | `Image.applyDisplayFunction()` |
| `bmp.setPixel()` ループ | `Image.render()` |
| `Math.floor(bx / scale)` の最近傍縮小 | `render(-n)` / `Bitmap.scaled()`（双線形） |

`Image.render()` のシグネチャは `Bitmap render([int zoomLevel=1[, enableTransparency=true[, fast=false]]])`。**`zoomLevel` は PixInsight 共通のズーム規約で正が拡大・負が縮小**（`-2` が 1:2、`-3` が 1:3）。`-1` は内部予約値で使用不可。

#### プレビューは原寸（1:1）でレンダリングする

変換がネイティブになったことで、**`MAX_BITMAP_EDGE 2048` のような縮小上限を引き継ぐ理由が無くなった**。この上限は per-pixel ループが遅かったことへの対処だったと考えられる。

原寸でレンダリングする利点は 3 つある。

1. **淡い 1〜2 px の流星痕を縮小で壊さない。** 6024 → 2048 は 3 px に 1 つを拾う勘定で、最近傍なら軌跡が細切れになりうる。流星と衛星の判別はまさにこの細部を見る作業なので、判断材料を落としてはいけない
2. **座標系が 1 段減る。** `bitmapScale = 1.0` となり、`検出座標 ×8 → bitmap 座標 → 画面座標` の 3 段で済む（縮小を挟むと 4 段になる）
3. 全体表示は `fitToWindow`、細部は `ImagePreviewControl` のズームで見る。既存の操作系がそのまま使える

#### 実測結果（2026-08-17、`tests/pjsr/probe_preview.js`）

上記の方針を実測で確定させた。対象は正解フレーム DSC05443（6024×4024×3ch）。

**`render()` は速い。プレビューのボトルネックではない。**

| 処理 | 時間 |
|---|---|
| `ImageWindow.open()` | 271〜591 ms |
| `computeOrFetchProperty("Median")` + `("MAD")` | 445 ms（2 回目以降は 0 ms） |
| `new Image()` + `applyDisplayFunction()` | 430 ms |
| **`render(1)`（原寸 6024×4024）** | **17〜26 ms** |
| 合計（1 フレームを開いて原寸 Bitmap を得るまで） | **約 1.2 秒** |

`zoomLevel` の符号規約も実測で確認した。`-2` → 3012×2012、`-3` → 2008×1341、`-4` → 1506×1006、`-8` → 753×503 と、いずれも厳密に 1:|n| の縮小になる。

**縮小は流星痕を実際に壊す。** 軌跡上の輝度ピークを、軌跡から 15 px 離した並行線と比較した値（0〜255）。

| レンダリング | サイズ | 軌跡のピークコントラスト | 1:1 比 |
|---|---|---|---|
| `render(1)` | 6024×4024 | **108.5** | 100% |
| `render(-2)` | 3012×2012 | 79.4 | 73% |
| `render(-3)` | 2008×1341 | 21.1 | **19%** |
| `render(-3, true, true)` | 2008×1341 | 11.9 | 11% |
| `render(-4)` | 1506×1006 | 28.0 | 26% |
| `render(1)` → `Bitmap.scaled(1/3, Bilinear)` | 2008×1341 | 20.2 | 19% |

1:3 まで縮小するとピークが 5 分の 1 になる。**`manual-image-solver` が使っている 2048 px 上限（6024 → 約 1:3）は、まさにこの領域にあたる。**流星と衛星の判別は軌跡の細部を見る作業なので、この上限を引き継いではいけない。1:2 なら 73% を保つが、1:1 が 17 ms で得られる以上、縮小する動機が無い。

`fast` 引数は**縮小時のみ**効く品質・速度のトレードオフだった（`render(-3)` で 21.1 → 11.9 に劣化する代わりに約 2 倍速い）。原寸では時間・品質とも差が無い。原寸で使う限り気にしなくてよい。

補足: 平均コントラストは背景参照線の取り方が悪く（並行線が一貫して明るい領域に乗った）指標として使えなかった。上表のピークは、背景項が全条件でほぼ一定（110〜112）だったため条件間の比較としては妥当だが、1:3 と 1:4 の逆転が示すとおりサンプリング位置の当たり外れによる揺らぎがある。読み取ってよいのは「1:1 ≫ 1:2 ≫ 1:3 以下」という桁の差までである。

**原寸 Bitmap は 4 枚同時に保持できる。**

1 枚 92 MB、4 枚で 370 MB。確保は 1 枚 18 ms で、4 枚保持したあとも最初の 1 枚が読める。**LRU キャッシュは成立する。**

**ディスクキャッシュは採らない。**

| 保存内容 | 書き出し | サイズ | 読み込み |
|---|---|---|---|
| 原寸 PNG | 8148 ms | 47.3 MB | 568 ms |
| 1:3 PNG | 1020 ms | 5.1 MB | 62 ms |
| 1:3 JPEG (q=90) | 37 ms | 0.6 MB | 20 ms |

原寸 PNG は書き出しに 8 秒かかり、読み込みも 568 ms と XISF を開くのと変わらないため無意味。速いのは縮小した場合だけで、その縮小が上表のとおり軌跡を壊す。**「速いキャッシュは使えず、使えるキャッシュは速くない」ため、この選択肢は消える。**

#### 結論としてのプレビュー方針

- **原寸（1:1）でレンダリングする。** 縮小上限は設けない
- **ディスクキャッシュは持たない。** メモリ上の LRU（4 枚程度）で足りる
- **次の候補フレームを先読みする。** 人が現在のフレームを判断している数秒の間に読めば、体感は即座になる
- **STF は固定できるようにする。** Median / MAD の算出が 445 ms を占めるため、1 枚から求めた STF をセッション全体で使い回せば 1.2 秒 → 約 750 ms になる。WBPP も同じ理由で STF ロックを持つ

#### 座標変換（実装時の注意）

検出座標（1/8 縮小フィールド）から原寸への変換は、**単純な 8 倍ではない。**

```
full = (n + 0.5) * s - 0.5        s = 原寸幅 / 縮小幅
```

縮小フィールドのサンプル n は原寸の `[n*s, (n+1)*s)` を代表するので、その中心は `n*s` ではない。単純に掛けるとブロックの左上隅を指し、**最大 s/2 = 4 px ずれる。**流星痕は 1〜2 px 幅なので、この差で完全に外す。probe の初版が実際にこれを踏み、軌跡を捉えられていなかった。**オーバーレイのボックス描画とクリックのヒットテストで同じ変換を使う。**

#### 候補のオーバーレイ表示

**1 フレームに複数の候補が写ることは常態である。** 実データでも流星と衛星が同一フレームに同居し、最大 3 件が同時に出た。したがってプレビューは「線を 1 本描く」では足りず、**どれがどれか識別できる表示**が要る。

- **候補ごとにボックスと通し番号を描画する**。番号は候補リスト（TreeBox）の行番号と一致させる
- **チェックで選択していける**。プレビュー上のボックスと候補リストの行は双方向に連動させる（ボックスをクリックすると行が選択され、行を選ぶとボックスが強調される）
- 選択済み / 未選択 / 除外 を色で区別する
- 番号は軌跡に重ならない位置にオフセットして描く

**ボックスの形状は軸平行の外接矩形で始める。**

斜めの軌跡では軸平行の外接矩形が軌跡の数十倍の面積になるため、候補が密集すると重なって番号が読めなくなる懸念があった。軌跡に沿った回転矩形なら細く収まるが、実データで測ったところ**その状況は起きていなかった**。

2026-08-12 セッション（654 枚・候補 411 件）の実測。

| 1 フレームあたりの候補数 | フレーム数 |
|---|---|
| 0 件 | 363 |
| 1 件 | 204 |
| 2 件 | 62 |
| 3 件 | 18 |
| 4 件 | 6 |
| 5 件 | 1 |

```
同一フレーム内の候補ペア    162 組
軸平行ボックスが重なるペア    0 組（0.0%）
```

候補が出るフレームの 87% は 1〜2 件で、最大でも 5 件。**重なりは 1 組も無い。** 軸平行で十分である。

（測定は端点から矩形を復元して行った。実際の外接矩形は軌跡の幅の分だけわずかに大きいが、結論を変える差ではない。）

ただしこれは 1 セッションの結果である。Starlink トレインのように平行な軌跡が並ぶ場合や、より緩い閾値で候補数が増えた場合は状況が変わりうる。**実際に重なりが問題になってから回転矩形を検討する**（UI 側の工夫、たとえば番号の引き出し線やホバーでの強調で解決する可能性もある）。

#### 正解データ作成モード（Phase 1 スコープ）

**「この候補が流星である」と記録して正解データを書き出す機能を持たせる。**

検出性能の評価には候補単位の正解が要るが、座標を人手で入力させるのは筋が悪い。人にしか出せない情報は「複数の候補のうちどれが流星か」という判断だけで、座標はその候補が既に持っている。UI は候補を表示して採否を判断させるものなので、この機能はその自然な拡張になる。

**自作自演を避けるための必須要件**:

- 正解作成モードでは**全候補を表示する**。衛星フィルタやスコアで絞り込まない
- **分類器の判定・スコアを表示しない**、または隠せるようにする
- 表示順を分類器のスコア順にしない（提示順自体が誘導になる）

分類器の出力を見せた状態で人に選ばせ、その正解で同じ分類器を評価すると、データセット規模の自作自演になる。通常のスクリーニングモードでは絞り込みとスコア順が有用なので、**2 つのモードは明確に分ける**。

詳細は [docs/tests.md](tests.md) 5-2 を参照。

#### モードは起動時に選び、実行中は切り替えられない（2026-08-17 決定）

**正解作成モードでは、分類スコア列・分類判定列を UI に持たせない。**後から表示するスイッチも設けない。切り替えるにはダイアログを開き直す。

実行中に切り替えられると、正解を付けている最中にスコアを見に行けてしまい、「分類器の出力を見せない」という要件が実質的に無効になる。禁止する UI を作るより、**その列が存在しない UI を作るほうが確実で、実装コストもほぼゼロ**である。

| | 通常スクリーニング | 正解データ作成 |
|---|---|---|
| 検出パラメータ | 運用値 | 運用値より緩い値 |
| 表示する候補 | 絞り込み可（`persistent` を隠す等） | **全候補** |
| スコア列・分類列 | あり | **無し（存在しない）** |
| 既定のソート順 | スコア順 | **フレーム順（撮影時刻順）** |
| 出力 | セッション JSON | `ground_truth.json` 形式 |

#### 判定は 4 状態で記録する（2026-08-17 決定）

採否のチェックボックス（2 値）では足りない。`docs/tests.md` 5-4 が「**判断に迷ったフレームは `uncertain` として分離し、指標の分母から外す**」と定めており、これは 2 値では表現できない。曖昧なものを正解に含めるとベースラインが不安定になる。

| 状態 | 意味 | 評価上の扱い |
|---|---|---|
| `unreviewed` | 未判定（初期値） | 分母に含めない |
| `meteor` | 流星 | recall の分子・分母 |
| `not-meteor` | 流星ではない（衛星・飛行機・その他） | `known_false_positives` に記録 |
| `uncertain` | 判断できない | **分母から外す** |

`not-meteor` をさらに衛星／飛行機／その他に細分することは**しない**。判定操作が増えると 94 枚をめくる速度が落ちる。Phase 2 の分類器評価で内訳が必要になった時点で、`not-meteor` の候補だけを対象に別途ラベリングすればよい。

#### 候補リストは候補単位のフラットな一覧にする

フレーム単位ではなく候補単位で並べる。1 フレームに複数の候補が出るのは常態（実測で最大 5 件）であり、判定の単位も候補だからである。フレーム→候補の 2 階層ツリーにするとソートが階層に閉じてしまい、「長いものから確認する」といった横断的な並べ替えができない。

列は `# / File / Time / Length / Angle / Elong / Track / Verdict`。`Track` はフレーム横断照合の軌跡長で、`persistent`（`maxMeteorFrames` 超え）が一目で分かる。`#` はゼロパディングした通し番号とし、ソート後も元の番号を保持する（`manual-image-solver` と同じ手法）。**この番号がプレビュー上のボックス番号と一致する。**

#### キーボードだけで判定できること

94 枚をめくる作業なので、マウスに手を戻させない。

| キー | 動作 |
|---|---|
| `M` | `meteor` にして次の候補へ |
| `N` | `not-meteor` にして次の候補へ |
| `U` | `uncertain` にして次の候補へ |
| `Space` | 判定せず次へ |
| `←` / `→` | 前後の候補へ移動 |

判定と同時に次へ進むのは、判定→移動の 2 操作を 1 操作にするため。取り消しは `←` で戻って付け直す。

### 7.1.9 Stage 3 / 4 の実装と実データでの検証（2026-08-17）

`javascript/trail_mask.js` と `javascript/composition.js` を実装し、`tests/pjsr/run_composite.js` で実データを通した。演算はすべて純粋 JS 側にあり、PJSR には画素の出し入れだけが残る。

#### マスクの形状はカプセル

端点間の線分を半径で太らせたもの。

- **回転矩形では端が切れる。** 流星が増光・減光する丸い先端がちょうど落ちる
- **軸平行矩形では面積が数十倍になる。** 斜めの軌跡で顕著で、余分な画素はすべて、はるかに清浄な master にサブフレームのノイズを持ち込むことになる

**端点は「検出閾値を下回った所」であって「発光が止まった所」ではない。** そのため軌跡方向へ延長してから太らせる。延長しないと淡い先端が切れ、そこはまさに流星の増光・減光が見える部分である。

フェザーは smoothstep。**線形ランプでは両端で傾きが残り、空と接する所に折れ目ができる** — 継ぎ目を消すために入れたものが継ぎ目を作る。

#### 実測（654 枚・採用 31 本）

| 項目 | 結果 |
|---|---|
| 合成できたフレーム | **30 / 31** |
| 処理時間 | 114.8 秒（約 3.8 秒/枚） |
| フィットのスケール | 1.05〜1.17（全チャンネル） |
| 合成マスクの面積 | 画面の 4.77%（1,157,110 画素、うち中実 456,654） |

#### 出力の正しさを検証した

**誤ったコンポジットは正しいものと見分けがつかない。** マスクの位置がずれても、フィットの相手が違っても、出力は「流星が写った空の絵」になる。そのため `tests/pjsr/verify_composite.js` で、正しさを定義する性質を書き出したファイルに対して直接検査した。

1 つ目が比較明合成を却下した判断の裏付けである。**マスクの外では master が 1 ビットも変わっていない。**

マスク内で 13.4%（464,933 / 3,471,330）のサンプルが暗くなっているのは**正常**で、残差がサブフレームの対称なノイズを含むためである。クリップすると空が持ち上がる（7.3 参照）。平均が正であることが要件で、全サンプルが明るくなることではない。

### 7.1.10 マスク寸法の実測と合成方式の修正（2026-08-18）

7.1.9 のコンポジットを目視確認して、2 つの問題が報告された。**マスクが大きすぎて合成部分が目立つ**、そして**2 枚にまたがった流星の周りが真っ黒に抜ける**。どちらも実測で原因を確定させ、方式を修正した。

#### マスクは 10 倍過大だった

`tests/pjsr/probe_trail_profile.js` で、採用 31 本それぞれの残差（`sub − fit(master)`）を軌跡の軸からの距離ごとに平均した。

| 軸からの距離 | 残差の平均 | 残差ノイズとの比 |
|---|---|---|
| 0 px | 9.20e-4 | 5.2σ |
| 5 px | 1.75e-4 | 1.0σ |
| 15 px | 9.03e-5 | 0.51σ |
| **20 px** | 1.62e-5 | **0.09σ** |
| 53 px | 約 5e-6 | 0.03σ |

端点より先（軸方向）は、端点上で 0.87σ、8 px 先で 0.38σ、10 px でノイズに沈む。

**流星の光は軸から 20 px で完全に消える。** 従来のマスクは軸から中央値 53 px（`analyze_mask.js` 実測、画面の 5.18%）まで開いており、外側 2/3 は流星の光を 1 つも含まず、サブフレームのノイズだけを master に持ち込んでいた。

| パラメータ | 変更前 | 変更後 | 根拠 |
|---|---|---|---|
| `coreRadius` | 8 | **5** | 光が 1σ に落ちる距離 |
| `featherWidth` | 32 | **15** | 合計 20 px で光が 0.09σ |
| `endExtension` | 16 | **10** | 端点から 8 px で 0.38σ |
| `coreScale` | 2.5 | **0** | 下記 |

**`minorLength` に係数を掛ける方式は棄却した。** 1/8 縮小場で測った幅なので、1〜2 px の軌跡はサンプル未満であり、返ってくるのは軌跡の幅ではなくサンプル格子の大きさである。実測は無相関で、幅 43 px と測れた候補（DSC05317）の光は 3 px、幅 8 px の候補（DSC05440）の光は 4 px だった。ピーク輝度は 100 倍の幅（0.0024〜0.264）があるのに幅との相関は現れない。**オプションとしては残す**（この結論は 1/8 場に対するもので、他の機材構成には当てはまらない可能性がある）。

結果として合成マスクは画面の **5.18% → 1.414%**、処理時間は 114.8 秒 → 35.6 秒になった（後者はフィットの間引きによる）。

#### 2 枚にまたがった流星が黒く抜けたのは累積が原因

**1 枚合成するたびに結果を master に書き戻していた。** つまり次のフレームは「流星が入った master」に対してフィットと残差を取る。

露出をまたいだ流星は 2 枚のマスクが重なる。重なった領域で 2 枚目を処理すると、

```
累積master = master + 1枚目の流星光
sub2      = その位置に流星は無い（流星は先へ進んでいる）
residual  = sub2 − scale × 累積master ≒ −scale × 1枚目の流星光
result    = 累積master + residual × mask ≒ master − 0.17 × 流星光
```

スケールが 1.05〜1.17 なので**加算した分より多く引かれる。** 流星のピーク加算量 0.0455 に対し master の空レベルは 8.3e-3 なので、0.17 倍でも空レベルとほぼ同じ。ゼロまで落ちて真っ黒になる。

`tests/eval/analyze_mask.js` で、31 本のうち**マスクが重なるペアが 4 組**実在することを確認した。うち 3 組は軌跡間の距離が 10 px 未満である。

| ペア | 軌跡間の距離 | 当時の合計リーチ |
|---|---|---|
| DSC05069 / DSC05070 | 7.8 px | 117 px |
| DSC05443 / DSC05444 | 5.4 px | 111 px |
| DSC05123 / DSC05292 | 9.8 px | 93 px |
| DSC05014 / DSC05426 | 105.2 px | 124 px |

**フィットと残差は常に手つかずの master に対して取る。** 加算分は別のアキュムレータに溜め、フレーム間は max で合成して最後に 1 回足す。max であって加算でないのは、2 枚の軌跡が接する部分で同じ光を二重に数えないためである。

#### 加算量を 0 でクリップする（比較明合成の採用）

7.3 で「素直な比較明合成（max）を使ってはならない」としていたが、**マスク内に限れば両者は等価である。**

```
mask 内で max(master, レベル合わせした sub)
  = master + mask × max(0, residual)
```

つまり比較明合成とは残差の負値クリップに他ならない。**そしてクリップしないことの代償のほうが大きかった。** 出力が master より暗くなる経路が残り、実際に上記の黒抜けを許した。

クリップの代償は持ち上がりである。対称なノイズの正側半分が残るので、マスク内の空が σ/√(2π) ≒ 0.4σ だけ持ち上がる。**実測 7e-5 に対し master 自身のノイズは 2.1e-4** なので、その 1/3 に収まる。マスクが 1.4% に縮んだこととあわせて、見えない量である。**この実測があるからクリップを選べる。**

却下理由として挙げていた「マスク内がザラつく」は、マスクを光の実際の広がりまで切り詰めたことで面積が 1/4 になり、成立しなくなった。

#### 局所背景を除去する

全画面 1 本の線形フィットは、サブと master の**局所的な空レベルの差**を吸収できない。残った誤差はマスクの形のまま出力に描き込まれる。実測では 1 本あたり最大 1.9e-4（master のノイズと同等）、フィットが破綻している DSC04908 では 3.2e-3 に達した。

マスクの外側のリング（幅 24 px）で残差の中央値を取り、加算前に引く。リングは合成が一切触れない画素なので、「確実に流星が無い場所での残差」を測っていることになる。平均でなく中央値なのは、星や別の軌跡が矩形の隅を掠めても動かないようにするため。

#### 検証（`tests/pjsr/verify_composite.js`）

| 検査 | 結果 |
|---|---|
| マスク外で master と厳密に一致するか | 差 **0.000e+0**、変化したサンプル **0 件**（2390 万画素 × 3ch） |
| **1 画素も暗くなっていないか** | **0 / 1,028,514** |
| チャンネル別の加算量 | R 1.399e-4 / **G 2.775e-4** / B 1.439e-4（平均） |
| 最も明るい加算の位置 | マスク値 **1.000** |

検査 2 は「マスク内の平均が正」から**「1 画素も暗くなっていない」に強化した。** 旧検査は黒く抜けている状態で PASS していた。**平均では穴が見えない。** これは 7.1.9 でチャンネル通算の検査がチャンネル別のバグを見逃したのと同じ誤りであり、2 度目である。

G の加算量が R・B の約 2 倍であることは、6.1.0 の「流星は緑に写る」と整合する。

### 7.1.11 マスクを光から作る（2026-08-18）

7.1.10 でマスクを実測値まで切り詰めたが、**さらに細めようとして計測したところ、幾何マスクそのものが成立しないことが分かった。**

#### 軸が痕からずれている

軌跡の軸から 2 px 以内に入る光量を候補ごとに出すと、0%〜92% と極端に割れた。光が広いのではなく、**仮定している軸が実際の痕からずれている。**

光で重み付けした符号付きの垂直オフセットを軌跡上の位置ごとに出すと、平行移動と回転の両方が現れた。

| 候補 | 長さ | 軸 2px 以内の光量 | 始点のずれ | 終点のずれ |
|---|---|---|---|---|
| DSC05069 | 242 | 84% | +1.2 | −2.1 |
| DSC05542 | 88 | 92% | −1.1 | +0.3 |
| DSC05070 | 206 | **4%** | +1.2 | **+8.1** |
| DSC05443 | 261 | **0%** | **−8.7** | −2.7 |
| DSC05409 | 221 | 96% | −0.7 | **−12.1** |
| DSC05014 | 444 | 11% | **−8.8** | +0.5 |
| DSC05281 | 653 | 7% | **−5.0** | **+5.3** |

ずれの中央値は 3.8 px、8 本が 10 px 以上。**検出は 1/8 縮小場なので端点に ±4 px の量子化があり、長い痕では傾きの誤差が遠端で開く。**

**太いマスクが軸ずれを隠していた。** 半径をどう調整しても解けない問題であり、単純に細めれば 31 本中 8 本で痕を外す。

#### 爆発（terminal flash）はこのデータには無い

一定半径のカプセルは、1 か所だけ丸く広がる爆発を切る。しかし実測では、**最も明るい DSC05069（ピーク 0.264、2 位の 3.5 倍）でも軸から 5 px 以内に 94% が入る。**

位置ごとの計測で「リーチ 33 px」等と出たビンは**星**だった。マスターとサブで PSF とレジストレーションがわずかに違うため、残差は星の位置でゼロにならない。リーチの大きいビンほどビンのピークが小さいという逆転がその証拠である。**この指標は星に汚染されるので、囲い込み光量で見ること。**

より明るい火球のデータが来たときの課題として残す（10 章の未決事項）。

#### マスクを残差から作る

カプセルは**「探す範囲（corridor）」**になった。軸から 25 px、軸方向に 25 px 延長。マスクではなく、フィットと局所背景リングから軌跡を外すために使う。

マスクは残差そのものから作る。

1. **3 チャンネルの残差を平均する。** マスクは 1 つで、光の位置は全チャンネル共通なので、平均するとノイズが 1/3 になる。加算する光は各チャンネル自身のもので、共有するのは「どこに」だけ
2. **5×5 の箱で平滑化する。** 痕の光は隣接画素で相関し、ノイズはしない。ノイズだけが 1/5 になる
3. **平滑化ノイズの 3σ〜5σ で smoothstep 閾値。** フェザー幅を別に持つ必要が無い。光自体が滑らかに落ちるので、閾値を滑らかにすれば縁も滑らかになり、しかも**光が終わる所で終わる**
4. **芯（軸から 3 px）と、軸から 15 px 以内の 5σ 超の画素を種にして、3σ 超の領域を 8 近傍で成長させる。** 孤立したノイズは入らない

`kLow` は 2 では駄目だった。1 本あたり約 170 px のノイズが芯から成長して入る（平滑化場の 2.3% が 2σ を超え、8 近傍で連鎖する）。**3 なら 0.13%** で、捨てるのは既に画素ノイズの半分を切っている裾だけ。

**芯は光が無くても常に 1 にする。** 閾値をどこでも超えない淡い痕があった場合にマスクが空になり、採用した流星が黙って消えるのを防ぐため。軸がずれていれば空を 6 px 幅で覆うが、クリップ後の持ち上がりは 0.4σ で master のノイズの 1/3 なので見えない。**「黙って消える」ほうが「見えないノイズを足す」より遥かに悪い。**

#### 書き出し先を 1 か所にまとめる（2026-08-18）

「`Run detection` の出力パスはどう決まるのか」「自動保存のパスはどう決まるのか」という問いから、**GUI の検出経路が一度も動かされていなかった**ことが分かった（検出はヘッドレスの `run_detection.js` でしか回していない）。調べると 2 つ壊れていた。

どちらも UI から見えないので気づけなかった。**パスは見える所に置く。**

`Source` グループを **`Source / Destination`** に改め、`Output:` の行（テキスト＋`Browse...`）を追加した。ここに `detection_results.json`・`meteor_session.json`・コンポジットのすべてが入り、**frames ディレクトリには何も書かない。** 既定値は frames の親（親が `registered` なら更にその上。WBPP は `<root>/registered/<group>/` に置く）で、Settings に保存される。操作者が自分で選んだ場合は、frames を変えても上書きしない。

中断した検出は `cancelled: true` と `framesRequested` を記録する。**部分的な結果ファイルは完全なものと見分けがつかず**、`evaluate.js` がそれを完全な結果として採点すると「検出器の劣化」に見える recall を報告する。`evaluate.js` 側でも警告を出すようにした。

```
*** Error: .../paths.js, line 44: Unterminated block comment.
```

**`node --check` は通る**（JS としては正しい）。プリプロセッサだけが誤読する。ディレクトリ構成を説明するコメントにグロブを書くのは自然な書き方なので、`tests/ut/test_module_isolation.js` に静的検査を追加した。文字列リテラル内の `/*` は問題ない（`FileFind` に `dir + "/*"` を渡すのは全域で使っている）ため、文字列を除いてから検査している。

パス処理は `javascript/paths.js` に切り出して Small テストを付けた。**そのテストが即座に本物のバグを見つけた**: `baseName` は末尾の区切りを剥がすのに `directoryOf` は剥がしていなかった。`GetDirectoryDialog` が `.../registered/group/` を返すと親が `.../registered/group` になり、`registered` 判定が外れて**出力先が frames ディレクトリそのものになる**。いま防ごうとしていた事故が別経路で起きるところだった。

### 7.1.12 選択行は再構築を跨いで意味を持たない（2026-08-19）

操作者の報告: **`Show` を触ったところから動きがおかしくなり、コンソールにエラーが出る。**

```
*** Error: MeteorComposer.js:3121: TypeError: Cannot read properties of undefined (reading 'file')
   || this.displayed[this.currentRow].file !== this.displayed[index].file;
   at Dialog.selectDisplayed
   at candidateTree.onCurrentNodeUpdated
```

`refreshList()` の末尾が原因だった。

```js
var target = this.currentRow;
if (target < 0 || target >= this.displayed.length) {
   target = 0;          // target は直すが currentRow は古いまま
}
this.selectDisplayed(target, true);
```

`selectDisplayed` は `this.displayed[this.currentRow]` を読むので、**フィルタでリストが選択行より短くなると範囲外を読んで落ちる。** 一度落ちると以降の操作すべてで落ち続ける。

#### 位置ではなく候補を追う

そもそも**表示リストの位置は再構築を跨いで意味を持たない。** 411 件中の 40 行目と 92 件中の 40 行目は別の候補であり、存在しないこともある。行が持つ `id` は残るので、それで追う。

`session_model.js` に `indexOfRowId(displayed, id)` を足した（純粋関数なので Small テストで押さえられる）。フィルタが選択候補を隠した場合は -1 を返し、UI は先頭に戻る。**副産物として、フィルタを変えても同じ候補を見続けられるようになった**（従来は古い位置に居座る別の候補に飛んでいた）。

#### 不変条件はアクセサで守る

`this.displayed[this.currentRow]` を読む箇所が 6 つあり、**そのうち 4 つは `currentRow < 0` しか見ていなかった** — 問題だったことのない側の境界だけを守っていた。個々に上限を足すのではなく、読み出しを 1 か所に閉じた。

```js
currentDisplayedRow() {
   if (this.currentRow < 0 || this.currentRow >= this.displayed.length) {
      return null;
   }
   return this.displayed[this.currentRow];
}
```

**`tests/ut/test_module_isolation.js` が直接読みを禁止する静的検査を持つ。** アクセサ自身の 1 行だけを例外とし、それ以外の `this.displayed[this.currentRow]` があれば行番号付きで失敗する。意図的に戻して落ちることを確認済み。

これは**実行時の不変条件を静的に守れる形に変換した**例である。`MeteorComposer.js` は構文解析しかできない（PJSR のオブジェクトモデル全部が必要になる）ので、「読み方の規約」に落とせるものは落とすほうが検査が効く。

### 7.3 Stage 4 — コンポジット生成

#### 用語：Integration ではなく Composition

本操作は `ImageIntegration` ではなく `HDRComposition` に類する処理であり、**用語としては Composition を用いる**。

| プロセス | 意味 |
|---|---|
| `ImageIntegration` | N 枚を重み付き平均 / 中央値＋ピクセルリジェクションで統計的に 1 枚にする。目的は S/N 向上 |
| `HDRComposition` | 露出の異なる画像から、ピクセル単位で適切なものを選択して合成 |

本操作は「master light に、選ばれたサブの流星部分だけをマスク経由で加算」するもので、統計処理・リジェクション・平均・S/N 向上のいずれも伴わない。特定領域を特定フレームから選択的に持ってくる操作である。

UI・ドキュメントで "Integration" を用いると、PixInsight ユーザーに `ImageIntegration` の意味論（シグマクリップ、重み付け、リジェクションマップ）を期待させるため、積極的に誤解を招く。英語圏の天体写真でも "meteor composite" が定着した表現であり、"meteor integration" とは言わない。

#### 合成方法

**流星の光だけを加算する。**

```
fit    = LinearFit(master → sub)             ← マスクの外の空で決める
light  = sub − fit(master) − 局所背景         ← 0 でクリップする
result = master + フレーム間の max( light × feathered_mask )
```

背景は master の高 S/N のまま、流星の光成分だけが乗る。**マスク内では比較明合成と等価**であり（`master + mask × max(0, residual)` は `mask` 内の `max(master, レベル合わせした sub)` そのもの）、出力が master より暗くなることは構造的に起こらない。

~~**素直な比較明合成（max）を使ってはならない。** サブフレーム 1 枚は master light より遥かにノイズが大きいため、マスク内でも背景ノイズが master に勝ち、流星の周りだけザラつく。~~ — **2026-08-18 に撤回。** マスクを光の実際の広がり（軸から 20 px）まで切り詰めた結果、面積が 1/4 になってザラつきの根拠が消えた。逆に、クリップしないことで出力が master より暗くなる経路が残り、実際に黒抜けを許した。詳細と実測は 7.1.10 を参照。

制約:

- この段階は **registered サブ＋ master light が必須**
- 全フレーム共通の有効域を提示し、周辺の虫食いを防ぐ（3.3 の 2 参照）
- **各フレームは必ず手つかずの master に対してフィットする。** 合成結果に累積してはならない（7.1.10）

## 8. 非機能要件

### 8.1 性能

- 一晩あたり 500〜600 枚の registered 画像を実用的な時間で処理すること
- 6000×4000×3ch float32 で 1 枚あたり約 288MB。500 枚で 100GB 超の読み込みとなり、**I/O が最大のボトルネック**
- ピクセル演算は `Image` のネイティブメソッドに寄せ、JavaScript の per-pixel ループは連結成分ラベリングに限定する
- 進捗表示と中断機能を備えること

### 8.2 動作環境・配布

- **PixInsight 1.9.4 以降（V8 専用）**。SpiderMonkey（1.9.3 以前）には対応しない
- 外部依存なし（Python 不要、サードパーティ製プロセス不要）
- `pixinsight-scripts` リポジトリの updates.xri 経由で配信。`<platform version="1.9.4:9.9.9">` の 1 パッケージのみ
- CodeSign でスクリプトへ署名（開発者 ID `ysmr3104` は CPD 登録済み・署名運用中）

### 8.3 スクリプトメニューへの登録

機能カテゴリとベンダーカテゴリの両方に登録する。`#feature-id` は 1 つのディレクティブ内で `|` 区切りで複数のメニュー位置を指定できる。

```
#feature-id  MeteorComposer : Image Analysis > MeteorComposer | ysmrastro > MeteorComposer
```

PixInsight 純正スクリプト（`AnnotateImage : Astrometry > ... | Render > ...`）およびサードパーティの CosmicPhotons（`Utilities > ... | CosmicPhotons > ...`）が同じ方式を採っている。機能から探すユーザーと作者から探すユーザーの両方に届く。

#### 既存 2 本の同時掲載（Phase 1 リリース作業に含む）

**本スクリプトの公開に合わせて、ManualImageSolver / SplitImageSolver も `ysmrastro` カテゴリへ同時掲載する。** これにより `Script > ysmrastro` に 3 本が並ぶ。

```
#feature-id  ManualImageSolver : Astrometry > ManualImageSolver | ysmrastro > ManualImageSolver
#feature-id  SplitImageSolver  : Astrometry > SplitImageSolver  | ysmrastro > SplitImageSolver
```

機能カテゴリ（`Astrometry`）は残す。プレートソルバーを探すユーザーは標準の `Astrometry` を見るため、そこから外すと発見性が落ちる。

**必要な作業**（各ソースリポジトリ側）:

1. `#feature-id` 行を変更
2. パッチバージョンを上げる（例: ManualImageSolver 2.0.0 → 2.0.1）
3. PixInsight の CodeSign で `.js` に再署名
4. `build-*.sh` でパッケージを再ビルド
5. `pixinsight-scripts` で `integrate.sh` を実行し、`updates.xri` を再生成・再署名

**判断が必要な点**:

- **SpiderMonkey 版（ManualImageSolver 1.4.1 / SplitImageSolver 1.2.0）も更新するか。** 更新しない場合、PixInsight 1.9.3 以前のユーザーには `ysmrastro` メニューが出ない。3 本を並べて見せることが目的なので、MeteorComposer 自体が 1.9.4 以降専用である以上、**SpiderMonkey 版は据え置きでよい**と考えられる
- メニュー項目の変更だけで更新通知が飛ぶため、リリースノートに「機能変更なし、メニュー登録先の追加のみ」と明記する
- `#feature-id` を変更すると古いメニュー項目が残る場合がある。動作確認時は **Script > Feature Scripts** でのリフレッシュも試すこと

### PJSR API 実地調査の結果（2026-08-16 実施・確認済み）

PixInsight 1.9.4 (arm64) 上で `tests/pjsr/probe_*.js` を実行して確認した。以下はすべて実測。

#### ピクセルの一括アクセス

**`Image.getPixels()` / `setPixels()` / `toArray()` / `pixelValue()` は存在しない。** 代わりに `Image.toMatrix()` を使う。

```
Image → toMatrix() → Matrix → toArray() / toFloat32Array() / toFloat64Array()
```

`Matrix` は `.rows` / `.cols` / `.at(row, col)` を持ち、さらに `MAD` / `median` / `mean` / `stdDev` / `Sn` / `Qn` / `biweightMidvariance` などのロバスト統計を**ネイティブで**備える。`toImage()` で逆変換もできる。

`Image.getSamples()` / `setSamples()` も存在するが引数が必要（未調査）。`Image.sample(x, y)` は単一画素用。

#### 主要 API の可否

| API | 可否 | 備考 |
|---|---|---|
| `Image.getLuminance(Image)` | ○ | 引数の `Image` に 1ch で書き込む |
| `Image.resample(scale)` | ○ | 6024×4024 → 753×503 |
| `Image.toMatrix()` | ○ | **一括アクセスの正解** |
| `Image.binarize` / `median` / `MAD` / `mean` / `stdDev` | ○ | |
| `Image.convolve` / `crop` / `fill` / `assign` / `normalize` | ○ | |
| `IntegerResample.Average / Median / Maximum / Minimum` | ○ = 0 / 1 / 2 / 3 | **コンストラクタ側**にある。`prototype` 側には無い |
| `StarDetector` | ○ | 下記 |
| `LinearFit` / `PixelMath` / `MultiscaleLinearTransform` / `AutomaticBackgroundExtractor` / `Convolution` / `MorphologicalTransformation` | ○ | いずれも利用可能 |
| `ColorSpace.RGB` = 1 / `ColorSpace.Gray` = 0 | ○ | 旧 `ColorSpace_RGB` は廃止済み |

#### StarDetector

`stars(image)` は次のフィールドを持つオブジェクトの配列を返す。

```
x, y        重心座標（float）
pos         Point（.x / .y）
rect        Rect（.x0 .y0 .x1 .y1 ほか多数）— 星の境界矩形
srect       Rect — 構造の矩形（rect より一回り大きい）
flux, bkg, size, signal, mad
```

主なパラメータ: `structureLayers`(5) / `sensitivity`(0.5) / `peakResponse`(0.5) / `maxDistortion`(0.6) / `hotPixelFilterRadius`(1) / `noiseReductionFilterRadius`(0) / `fitPSF`(false) / `psfElliptic`(false) / `minSNR`(0) / `upperLimit`(1)。

`fitPSF = true` にすると `signal` と `mad` が有効値になり `size` が小数になるが、**PSF の長軸・短軸・角度は公開されない**。

#### 「星の実測伸長比を基準にする」方式の見直し（要検討）

**もともとの狙い**（4.2）: 伸長比の閾値を固定値にせず、その夜の星の実測伸長比を測って「星の N 倍以上」を条件にする。追尾がわずかにずれて星が伸びた夜でも、閾値が自動追従するようにするため。

**問題**: `StarDetector` は星の伸長比を返さない。返すのは `x` / `y` / `pos` / `rect` / `srect` / `flux` / `bkg` / `size` / `signal` / `mad` のみで、**`fitPSF = true` / `psfElliptic = true` にしても長軸・短軸・傾きは公開されない**（実測で確認）。

`rect` の縦横比では代用できない。**`rect` は軸平行**なので、45° 方向に伸びた星の外接矩形は正方形に近くなり、伸長比が 1.0 と読めてしまう。追尾ずれは任意方向に出るため、系統的に過小評価する。

**代替案**: `computeMoments` と `connectedComponents` は既に自前で持っているので、`StarDetector` が返した星の位置の周囲に対してそれを適用し、**流星と同じ指標で**伸長比を測る。新しい機構は不要で、指標の一貫性も保てる。

**優先度は判断できない（実データでは評価不能）。**

当初「固定閾値 6.0 で足りているので優先度は低い」と書いたが、これは誤りだった。2026-08-12 セッションの実測は次のとおり。

```
全候補 411 件   : 最小 6.0   中央 11.7   最大 38.1
正解の流星 9 件 : 最小 9.5   中央 14 前後  最大 35.7
```

**流星の伸長比の分布は、それ以外の候補の分布に完全に埋もれている。** 伸長比は流星と衛星・飛行機を分離していない（4.2 で予告したとおり）。分離を担っているのは横断照合だけである。

そのうえで閾値 6.0 の位置づけはこうなる。

| | 状況 |
|---|---|
| **流星に対する余裕** | **薄い。** 最小 9.5 に対し閾値 6.0 は 1.6 倍しかなく、10 に上げると取りこぼす。**上げられない** |
| **星に対する余裕** | **未検証。** 閾値の本来の役目は星（伸長比 ≒ 1）の排除だが、このデータは追尾が良好で星が点像のため、その性能が試されていない |

つまり**上げられず、かつ十分かどうかも検証できていない**。自動追従はまさにこの状況のための機能であり、優先度を下げる根拠は無い。

**このデータセットでは評価できない**という点が本質である。自動追従が効くのは追尾が乱れて星が伸びた夜だが、本データはその条件を一つも含まない。**最良条件のデータで「固定値で足りる」と結論するのは、機能が必要な場面を評価していないのと同じ**である。

判断には星が伸びたデータが要る。意図的に追尾を外した検証用データを撮る、あるいは固定撮影で NPF 上限付近のデータを用意するのが確実。

| 処理 | 時間 |
|---|---|
| `ImageWindow.open()` 1 枚 | **466 ms** |
| `getLuminance()` | 23 ms |
| `resample(1/8)` → 753×503 | 47 ms |
| `toMatrix()` + `toArray()` | 約 3.3 ms |
| `Matrix.at()` で 378,759 画素を走査 | 1 ms |
| `Image.MAD()`（全解像度） | 112 ms |

`StarDetector` は 1 枚 2.2 秒かかるため全フレームには使えない。2nd pass 限定という 4.3 の設計は妥当。
