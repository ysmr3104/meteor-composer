# MeteorComposer 機能要件

> ステータス: ドラフト（要件整理段階）
> 最終更新: 2026-08-16
> リポジトリ: `ysmr3104/meteor-composer` / スクリプト名: `MeteorComposer`

---

## 1. 目的

一眼カメラで撮影した流星群の連番画像から、流星が写ったフレームを自動検出し、人手によるスクリーニングを経て、最終的に流星群コンポジット画像を生成する PixInsight スクリプト。

既存の `atomcam-meteor-detector`（ATOM Cam の動画から流星検出する Python パイプライン）とは**別物**であり、検出ロジックの考え方を部分的に参考にするに留まる。入力が動画ではなく長時間露出の静止画連番であること、リアルタイム性が不要であること、WCS が利用できることから、アーキテクチャは共有しない。

### 既存資産との関係

| プロジェクト | 本プロジェクトとの関係 |
|---|---|
| `manual-image-solver` | **UI 部品を流用**（ImagePreviewControl、ソート可能 TreeBox、Settings API によるセッション保存、Export/Import） |
| `split-image-solver` | 広角非 rectilinear の知見。将来の WCS 連携（輻射点算出等）の基盤 |
| `atomcam-meteor-detector` | 検出パラメータの相場観、マスクによる領域除外の考え方を参考 |
| `pixinsight-scripts` | 配信リポジトリ。updates.xri への追加が必要 |

## 2. スコープ

### 対象に含む

- 一眼カメラ（フルサイズ / APS-C）で撮影した流星群の連番画像
- 赤道儀による追尾撮影
- 三脚による固定撮影（**NPF ルールを遵守し、星が点像に写っているもの**）
- WBPP で位置合わせ・デベイヤーまで済んだ registered 画像を入力とする

### 対象に含まない

- 星が線状に流れるレベルの固定撮影（NPF を大きく逸脱したもの）。StarAlignment が通らないため対象外とする
- 動画からの検出
- リアルタイム検出
- 電波観測・複数地点観測との連携

### 実装方針の制約

- **PJSR ネイティブで完結させる**。配布容易性のため、Python・外部プロセス・サードパーティ製プロセスに依存しない（`manual-image-solver` と同方針）
- ES5 スタイル（`var` のみ、アロー関数・テンプレートリテラル不可）
- V8 エンジン前提（`CoreApplication.processEvents()`、`TextAlignment.*` 等のクラス静的定数形式）
- コード・コメント・コンソール出力・UI テキストはすべて英語

## 3. 入力データの前提

### 3.1 入力ファイル

WBPP が出力する **registered 画像**（`<output>/registered/` 配下）。キャリブレーション済み・コズメティック補正済み・デベイヤー済み・位置合わせ済みの状態。

registered を入力とする理由:

| 段階 | 可否 | 理由 |
|---|---|---|
| 元 RAW | × | ホットピクセル・カラム欠陥・アンプグローが線状偽陽性の温床になる |
| calibrated / debayered（位置合わせ前） | × | 検出座標が最終コンポジットの座標系と一致せず、座標変換が必要になる |
| **registered** | **○** | コズメティック補正済みで偽陽性が少ない。検出座標がそのまま後段のマスク生成・コンポジットに直結する |
| master light（積分後） | × | 流星はリジェクションで既に除去されている |

registered ファイル名には元サブフレームのファイル名が保持されるため、「どの撮影サブに流星が写っているか」の追跡が可能。

### 3.2 撮影条件の推奨範囲（固定撮影）

固定撮影では視野が 15°/時 で流れるため、StarAlignment が成立し、かつ実用的な重なり（70〜80%）を確保できる範囲に撮影時間を制限する必要がある。

以下はフルサイズ・F2.8・画素ピッチ 4.3µm（≒24MP）を仮定した目安。

| 焦点距離 | 水平画角 | 推奨撮影時間 | NPF 目安 | 概算枚数 |
|---|---|---|---|---|
| 14mm | 104° | 〜2 時間 | 約 16 秒 | 約 450 枚 |
| 24mm | 74° | 〜1.5 時間 | 約 10 秒 | 約 570 枚 |
| 35mm | 54° | 〜1 時間 | 約 7 秒 | 約 550 枚 |
| 50mm | 40° | 〜45 分 | 約 5 秒 | 約 600 枚 |

補足:

- **超広角側は重なり率ではなく StarAlignment の変換モデルが先に限界を迎える**。14mm で 30° 回転させると単純なホモグラフィでは周辺が合わない。ドキュメントで distortion correction（スプライン）の有効化を案内すること
- NPF 遵守＝短時間露出のため、**どの焦点距離でも一晩の枚数は 500〜600 枚に収束する**。1 枚あたりの処理時間予算がそのまま総処理時間を決める

### 3.3 registered 固有の注意点

1. **WBPP は整列に失敗したサブを registered に出力しない**。雲・振動で落ちたフレームに流星が写っていても検知できない。スクリプトは「入力サブ数 N / registered M / 未検査 N−M 枚」を明示的に警告すること
2. **無効領域（ゼロ埋め）が参照フレームからの時間差に比例して増える**。固定撮影では顕著。検出時に除外し、コンポジット時には全フレーム共通の有効域を提示すること
3. **補間リンギング**。StarAlignment の Lanczos overshoot により明るい星の周囲に正負のリングが残る

## 4. 検出アルゴリズム

### 4.1 方式の選択：単フレーム線検出

**参照差分方式（対象フレームから参照画像を引いて残差で検出する方式）は採用しない。**

参照差分には以下の 3 通りがあるが、いずれも本用途では割に合わない。

| 参照の作り方 | 呼称 | 備考 |
|---|---|---|
| 前後の隣接フレーム | 隣接フレーム差分 | `atomcam-meteor-detector` の方式 |
| 前後 ±N 枚の中央値 | ローリング中央値差分 | 隣接差分より頑健 |
| 全フレーム中央値 / master light | マスター差分 | 参照の S/N が最も高い |

**不採用の理由:**

- 参照差分が消してくれるのは星と静的構造だが、そこは伸長比フィルタで自明に落ちる（星は伸長比 ≒1、流星は数十以上）
- **本当に難しいのは衛星・飛行機の除外であり、これらは transient なので差分では消えない**。難しい問題に効かない
- **固定撮影で地上景が入ると破綻する**。registered 座標系では地上物が動くため、master light に地上物が流れて写り、差分すると輪郭が巨大な残差になる
- master light の存在が前提となり、WBPP を最後まで回さないと検出が始められない

**採用する方式：registered 1 枚の中だけで完結する線検出。**

```
背景除去（大スケール成分のモデルを引く）
  → 閾値化（残差の MAD から kσ）
  → 連結成分ラベリング
  → 各ブロブの 2 次モーメント → 伸長比・方位角・長さ・始終点
```

参照画像を作らず、前後フレームも読まないため、500 枚を 1 枚ずつ読み捨てられる。メモリ・I/O とも最小。

参照差分は、判定が微妙な候補に対する second opinion として**任意適用のオプション**に留める。

### 4.2 星と流星の分離根拠

24mm フルサイズ（6000px 幅、水平 74°）で 1px ≒ 0.74 分角。

| | 星 | 流星 |
|---|---|---|
| 形状 | 円形、FWHM 2〜5px | 直線 |
| 長さ | — | 1° の短いものでも約 80px、5° なら約 400px |
| 伸長比 | ≒1 | 数十〜数百 |

分離マージンは極めて大きく、参照差分に頼る必要がない。

**星の実測伸長比を基準にする。** `StarDetector` から得た星の伸長比を測定し、固定閾値ではなく「星の伸長比の N 倍以上」を判定条件とする。これにより「NPF をある程度遵守」レベルの軽微な追尾ズレにも自動追従する。

### 4.3 2 パス構成

```
1st pass（全 500 枚 / 1/8 縮小）
  輝度抽出 → 縮小 → 背景除去 → マスク適用 → 閾値 → 連結成分 → 伸長比
  星処理なし。安く広く拾う

2nd pass（1st を通過した数枚 / 原寸）
  StarDetector → 星・回折スパイク棄却 → 共線マージ
  → 始終点座標・長さ・方位角・輝度プロファイル抽出

3rd pass（候補リスト上のみ、画像読み込み不要）
  フレーム横断の候補照合 → 衛星・飛行機の判定
```

**ダウンサンプルは線状天体にとって不利にならない。** 1/8 に落とすと流星の輝度コントラストは約 2.7 倍下がるが、ノイズは 8 倍下がるため S/N はむしろ約 3 倍改善する（線に沿ったビニングに相当）。一晩の流星は数本〜数十本なので、2nd pass の対象は数枚に収まり、実質コストは 1st pass のみ。

### 4.4 背景除去

大スケールの明るさムラ（光害、月明かり、天の川、周辺減光の残り）を除去し、閾値を 1 本の値で決められるようにする。

採用手法は**強くダウンサンプルして元サイズに戻し、差分を取る**方式。

```
検出用画像 (750×500)
  → さらに 1/8 に縮小 (94×63)   ← 細い線が消え、背景だけが残る
  → 750×500 に拡大し戻す         ← 背景モデル
  → 検出用画像 − 背景モデル       ← 平坦化された残差
```

- 縮小時に median を使えば、流星や星がモデルに混入しない
- 既に 1/8 に落とした画像上で走るためコストはほぼゼロ
- ABE や MultiscaleLinearTransform は 500 枚に対しては過剰

### 4.5 閾値決定

平坦化された残差の MAD から `k × 1.4826 × MAD` で自動決定する。流星が占める画素は全体のごく一部のため、MAD は流星に汚染されない。

`k` をユーザー向けの主要な感度パラメータとして公開する。

### 4.6 星起因の偽陽性への対処（2nd pass）

伸長比だけでは落ちない、星に起因する偽陽性を潰す。

1. **回折スパイク** — 絞った明るい星から伸びる十字の光条。本物の直線なので形状では区別できない
2. **密集星野での星の連結** — 天の川では閾値化した星同士が隣接して数珠つなぎになり、細長い塊になる
3. 飽和星のブルーミング、レンズゴースト、ハロー

`StarDetector`（PJSR ネイティブの C++ オブジェクト。StarAlignment が内部で使うのと同じもの）で星の位置・明るさ・サイズを取得し、以下を適用する。

- **星の領域をゼロにしてはならない。** 流星が星の上を通過している場合、そこで途切れて 2 本の短い線に分断される
- 連結成分とモーメントを取った**後**に、候補の重心が検出済みの星と一致すれば星として棄却
- 線状候補の中心が明るい星の位置と数 px 以内で一致すれば回折スパイクとして棄却
- 分断された候補は**共線マージ**（同一直線上の断片を 1 本に統合）してから評価する

**1st pass では星マスクは不要。** 1/8 に落とすと FWHM 3px の星は 0.4px となりノイズフロアに埋もれる。密集星野の連結も縮小平均でなだらかな背景に変わり、背景除去で落ちる。縮小自体が星除去として機能する。

## 5. 検出対象エリアの除外

### 5.1 前提：registered 座標系では地上線が回転する

- **赤道儀追尾** — カメラが星を追うため生フレーム上で地上が動く。registered ≒ 生フレーム座標なので、地上線は傾いているうえに回転する
- **固定撮影** — 生フレーム上では地上は静止するが、星基準に揃えた registered 座標では地上が回転する

**どちらの撮影方式でも、registered 上の地上線は一晩を通して同じ位置に留まらない。** 回転量は向きと緯度に依存し、南中付近を向いていると速く、天の北極付近なら遅い。1〜2 時間で数十度変わることもある。

`atomcam-meteor-detector` の「下部 15% を除外」という固定値が成立していたのは、ATOM Cam が固定でカメラ座標のまま処理していたため。本プロジェクトでは座標系が異なる。

### 5.2 3 段構成

**Tier 1 — 静的な半平面**（優先度：高）

回転可能な直線 1 本で画面を二分し、片側を除外。パラメータは `角度 θ` と `オフセット d`。短時間セッション、または余裕を持ってマスクする運用ならこれで足りる。

**Tier 2 — キーフレーム補間**（優先度：高）

先頭フレームと末尾フレームで直線を設定し、間はタイムスタンプで線形補間。回転に追従でき、WCS も撮影地情報も不要。実装コストが低い割に効果が大きい。

**Tier 3 — WCS からの自動地平線算出**（優先度：中）

プレートソルブ済みなら各ピクセルの赤経赤緯が分かるため、`DATE-OBS` と観測地の緯度経度から全ピクセルの高度角を計算し、指定高度以下を自動除外する。フレーム毎に厳密に追従する。既存の solver 資産が活きる部分。

ただし **Tier 3 が消せるのは幾何学的な地平線のみ**で、地平線より上に突き出す木や建物は消せない。Tier 3 を実装しても Tier 1/2 の手動マスクは併用が必要。

### 5.3 形状

実際の風景は「左に木立、右に建物、下に地面」のように複数方向から張り出す。

- **回転可能な半平面を複数本、AND / OR で組み合わせる**（優先度：高）— 実装が軽く、多くのケースをカバーできる
- **マスク画像の読み込み**（優先度：中）— 任意形状の逃げ道。`atomcam-meteor-detector` に既存の機能
- 多角形指定（優先度：低）— より自由だが UI コストが高い

### 5.4 実装上の必須事項

**除外領域は「検出しない」だけでなく、統計計算からも外さなければならない。**

- **MAD 計算より前にマスクを適用する。** 明るい地上景（街灯、ライトアップされた建物）が統計に入ると MAD が引き上げられ、空側の検出感度が丸ごと落ちる
- **背景モデル生成時にも地上を除外する。** 含めると空側の背景推定が歪む

この処理順序は間違えやすいので、実装時・レビュー時のチェック項目とする。

### 5.5 UI

`manual-image-solver` の `ImagePreviewControl` を流用する。

- プレビュー上に直線をオーバーレイ描画し、除外側を半透明でシェーディング
- ドラッグで直線を操作（既存のクリック / ドラッグ判別ロジックを流用）
- 角度・オフセットの数値入力も併設
- **除外面積の実測値を表示**（例：「除外領域が画面の 32% を占めています」）。マスクし過ぎに気付けるようにする

## 6. 衛星・飛行機の除外

### 6.1 判別に用いる特徴量

| 特徴量 | 流星 | 衛星 | 飛行機 |
|---|---|---|---|
| **他フレームでの再出現** | 通常 1 フレームのみ | 連続フレームに連続的に移動して出現 | 同左 |
| フレーム貫通 | 途中で始まり途中で終わる | 端から端まで貫くことが多い | 同左 |
| 輝度プロファイル | 増光→減光、非対称。爆発痕あり | ほぼ一定 | ストロボで等間隔の破線 |
| 色（OSC） | 白〜青緑 | 白 | 航法灯の赤 / 緑が混じる |
| 同一フレーム内の平行線 | 単独 | Starlink トレインは平行多数 | — |

**最も強力なのは「他フレームでの再出現」。** 衛星も飛行機も連続する複数フレームに写り、位置が滑らかに移動する。流星は基本 1 フレームで終わる。形状特徴より遥かに効く。

実装上は、画像の再読み込みは不要で、**各フレームから抽出済みの候補の座標リスト同士を突き合わせる**だけで完結する（3rd pass）。

### 6.2 パラメータ設計

- 各特徴量に個別の閾値（詳細設定）
- それらを重み付けした**総合スコア＋ 1 本のカットオフスライダー**（通常操作）
- プリセット 3 段階（緩い / 標準 / 厳しい）

**デフォルトは「取りこぼさない側」に振る。** 後段に人間のスクリーニングが控えているため、飛行機が 30 本混じることより流星を 1 本落とすことの方が損失が大きい。厳しくしたいユーザーだけがスライダーを動かす設計とする。

## 7. 段階構成と成果物

```
Stage 1  検出            全フレーム走査 → 候補リスト（JSON 永続化）
Stage 2  スクリーニング    リスト＋プレビュー表示 → 人が採否をトグル → 確定
Stage 3  マスク生成       採用候補ごとに流星痕マスクを生成・出力
Stage 4  コンポジット      master light に流星だけを合成
```

Stage 1 と 2 の間で JSON に永続化することで、検出をやり直さずにスクリーニングだけやり直せる。

### 7.1 Stage 2 — スクリーニング UI

`manual-image-solver` の資産をほぼそのまま流用できる。

- **候補リスト** — ソート可能な TreeBox（`headerSorting = true`）。列は フレーム名 / 時刻 / 長さ / 方位角 / スコア / 分類 / 採否チェックボックス。スコア順ソートで上から確認できる
- **プレビュー** — `ImagePreviewControl`（ScrollBox、ズーム / パン、オートストレッチ）。検出した線をオーバーレイ描画
- **セッション保存・復元** — Settings API
- **Export / Import** — 候補リストの JSON 入出力

### 7.2 Stage 3 — 流星痕マスク生成

採用された候補ごとに、流星痕の領域を示すマスク画像を生成する。

- マスク境界は**必ずフェザリング**（ぼかし）する。継ぎ目が見えるため
- 出力形式・出力先は設定可能とする
- **Stage 4 が成立しない場合の逃げ道**として、Stage 3 の「マスク＋該当サブフレームの出力」で処理を止め、合成をユーザーに委ねる運用を許容する

### 7.3 Stage 4 — コンポジット生成

#### 用語：Integration ではなく Composition

本操作は `ImageIntegration` ではなく `HDRComposition` に類する処理であり、**用語としては Composition を用いる**。

| プロセス | 意味 |
|---|---|
| `ImageIntegration` | N 枚を重み付き平均 / 中央値＋ピクセルリジェクションで統計的に 1 枚にする。目的は S/N 向上 |
| `HDRComposition` | 露出の異なる画像から、ピクセル単位で適切なものを選択して合成 |

本操作は「master light に、選ばれたサブの流星部分だけをマスク経由で加算」するもので、統計処理・リジェクション・平均・S/N 向上のいずれも伴わない。特定領域を特定フレームから選択的に持ってくる操作である。

UI・ドキュメントで "Integration" を用いると、PixInsight ユーザーに `ImageIntegration` の意味論（シグマクリップ、重み付け、リジェクションマップ）を期待させるため、積極的に誤解を招く。英語圏の天体写真でも "meteor composite" が定着した表現であり、"meteor integration" とは言わない。

#### 合成方法

**素直な比較明合成（max）を使ってはならない。** サブフレーム 1 枚は master light より遥かにノイズが大きいため、マスク内でも背景ノイズが master に勝ち、流星の周りだけザラつく。

**流星の光だけを加算する方式を採用する。**

```
residual = sub − LinearFit(master → sub)     ← 流星の光だけが残る
result   = master + residual × feathered_mask
```

背景は master の高 S/N のまま、流星の光成分だけが乗る。

制約:

- この段階は **registered サブ＋ master light が必須**
- 全フレーム共通の有効域を提示し、周辺の虫食いを防ぐ（3.3 の 2 参照）

## 8. 非機能要件

### 8.1 性能

- 一晩あたり 500〜600 枚の registered 画像を実用的な時間で処理すること
- 6000×4000×3ch float32 で 1 枚あたり約 288MB。500 枚で 100GB 超の読み込みとなり、**I/O が最大のボトルネック**
- ピクセル演算は `Image` のネイティブメソッドに寄せ、JavaScript の per-pixel ループは連結成分ラベリングに限定する
- 進捗表示と中断機能を備えること

### 8.2 動作環境・配布

- PixInsight 1.8.9+（V8 エンジンの機能を使う場合は 1.9.4+ を要検討）
- 外部依存なし（Python 不要、サードパーティ製プロセス不要）
- `pixinsight-scripts` リポジトリの updates.xri 経由で配信
- CPD 登録完了後にスクリプトへ署名

### 実装前に確認が必要な PJSR API
